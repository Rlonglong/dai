# 04 · 帳號、權限與分支保護

給 GitLab 管理員。新人加入、離職移除、分支保護怎麼設、review 該看什麼。

---

## 1. 角色對照

GitLab 使用者由 Keycloak（VM5）透過 OIDC 帶進來，帳號來源是公司 LDAP。
所以**不需要在 GitLab 上建帳號**，只需要在專案裡給權限。

| GitLab 角色 | 誰 | 能做什麼 | 不能做什麼 |
|---|---|---|---|
| **Guest** | 只需要看 pipeline 狀態的人 | 看 issue、看 pipeline | 看程式碼 |
| **Reporter** | 維運人員 | 看程式碼、看 pipeline、重跑 job（需另外授權） | push |
| **Developer** | 開發人員 | 開分支、push、開 MR、跑 CI | **push 到 `main`**、**合併 MR 到 `main`** |
| **Maintainer** | 資深開發、系統負責人 | 上述全部 + **合併到 `main`** + 改 CI/CD Variables | 刪專案 |
| **Owner** | 系統負責人 | 全部 | — |

> ★ 關鍵設計：**Developer 不能合併到 `main`** ★
> 這樣「有人 review 過」才是硬性的，不是靠自律。
> 開發者自己開的 MR，自己按不下 Merge 鍵。

## 2. 分支保護怎麼設

> 本節依 **GitLab CE（免費版）** 撰寫。CE 沒有 Merge Request Approvals，
> 實際能做到什麼、做不到什麼見第 3 節。

**UI 路徑**：
```
左側選單找到該 project（GitLab 介面上叫 Project，不叫 repo）
  → Settings → Repository
  → 展開 Protected branches → Add protected branch
```

### `main`（正式）

| 設定 | 值 | 為什麼 |
|---|---|---|
| Branch | `main` | |
| **Allowed to merge** | **Maintainers** | 開發者不能自己合併自己的 MR（★CE 底下這是最重要的一條★，見第 3 節） |
| **Allowed to push and merge** | **No one** | 任何人都不能直接 push，一律走 MR |
| Allowed to force push | ❌ 關閉 | 防止改寫已經部署過的歷史 |

### `develop`（測試）

| 設定 | 值 |
|---|---|
| Branch | `develop` |
| Allowed to merge | Developers + Maintainers |
| Allowed to push and merge | Developers + Maintainers |
| Allowed to force push | ❌ |

測試環境刻意放寬，讓開發者可以快速迭代。反正它只碰得到測試 DB
（見 [13_Variables與環境隔離](../進階調整/13_Variables與環境隔離.md)）。

### 驗證分支保護真的生效

```bash
git checkout main
echo "test" >> README.md && git commit -am "test: 驗證分支保護"
git push origin main
# 預期：remote: GitLab: You are not allowed to push code to protected branches
git reset --hard HEAD~1
```

看到 `You are not allowed to push` 才算設對。

## 3. Code Review 的強制性（CE 版）

需求是「**正式的一定都要 MR、被別人 code review 才能合併到主分支**」。

### 3-1. 先講清楚 CE 做得到什麼、做不到什麼

> 🚨 **GitLab CE 沒有 Merge Request Approvals。**
> `Settings → Merge requests` 這一頁只有 Merge method / Merge options /
> Squash / Merge checks 幾個區塊，**不會有「Approval rules」**。
> 也就是說：**作者可以自己開 MR、自己按 Merge，GitLab 不會擋。**

| 想要的效果 | CE | 靠什麼達成 |
|---|---|---|
| `main` 不能直接 push | ✅ | `Allowed to push and merge = No one` |
| pipeline 沒過不能合併 | ✅ | Merge checks 的 `Pipelines must succeed` |
| 討論沒解決不能合併 | ✅ | Merge checks 的 `All threads must be resolved` |
| 一定要有人核准才能合併 | ❌ | 見 3-3 的補償措施 |
| 作者不能自己核准自己 | ❌ | 同上 |

### 3-2. Merge checks（CE 唯一能強制的閘門）

**UI 路徑**：`該 project → Settings → Merge requests`

**Merge method**

| 選項 | 選不選 | 為什麼 |
|---|---|---|
| **Merge commit** | ✅ **選這個** | 每次合併留一個 merge commit，看得出「這批改動是一次 MR 進來的」，稽核與 rollback 都靠它 |
| Merge commit with semi-linear history | ❌ | 多一道 rebase 手續，歷史好看但不值得 |
| Fast-forward merge | ❌ | 不留 merge commit，MR 的界線在歷史上消失，很難一次退掉整批 |

**Merge options**

| 選項 | 勾？ | 為什麼 |
|---|---|---|
| Automatically resolve merge request diff threads when they become outdated | ❌ **不要勾** | 討論串會因為推了新 commit 就自動消失，等於「改了就當作審過了」 |
| Show link to create or view a merge request when pushing from the command line | ✅ | 純方便 |
| Enable "Delete source branch" option by default | ✅ | 合併後自動刪分支，也避免 D-Track 累積一堆廢棄的 project version |

**Squash commits when merging** —— 選 **Allow**（預設不壓縮，需要時作者自己勾）。
選 `Require` 會讓「誰在哪一步改了什麼」全部消失，不要選。

**Merge checks** ★這一區是重點★

| 選項 | 勾？ | 說明 |
|---|---|---|
| **Pipelines must succeed** | ✅ **必勾** | pipeline 沒綠燈就按不下 Merge。lint／資安掃描／D-Track 全靠這一條生效 |
| Skipped pipelines are considered successful | ❌ **絕對不要勾** | 勾了之後「pipeline 被 skip」也算通過，等於留一個後門 |
| **All threads must be resolved** | ✅ **必勾** | reviewer 提的問題不能不回應就合併 |

### 3-3. 我們的做法：`Allowed to merge = Maintainers`

**這是全篇統一的做法，不是選項之一。**

```
開發人員   = Developer 角色  → 只能開 MR，Merge 鍵是灰的、按不下去
系統負責人 = Maintainer 角色 → 只有他們按得下 Merge
```

設定位置就是 3-1 那張表裡 `main` 的 **Allowed to merge**。
效果上就是「**作者自己合不了，一定要另一個人動手**」——
CE 底下最接近強制 code review 的做法。

**驗證**（用 Developer 帳號實測）：
```
1. 用 Developer 角色的帳號開一個 MR
2. 等 pipeline 綠燈
3. 看 Merge 按鈕 → 應該是灰的，游標移上去會顯示沒有權限
```

**配套規定**（系統擋不住的部分，靠流程）：

| 規定 | 為什麼 |
|---|---|
| Maintainer 至少 2 人 | 一個人請假就全部卡住 |
| Maintainer 自己的 MR，由另一位 Maintainer 合併 | 系統不會擋，靠自律 |
| reviewer 要在 MR 開一個 thread 寫意見（`LGTM` 或具體問題） | 靠 `All threads must be resolved` 保證它被處理過，也留下審查痕跡 |
| 每月抽查 `該 project → Merge requests → 篩選 Merged` | 看有沒有「開了就自己合」「零討論」的 MR |

### 3-4. 高風險檔案怎麼把關

CE 沒有能「自動指定審查者」的機制，所以**高風險檔案完全靠 3-3 的
`Allowed to merge = Maintainers`**：Maintainer 按下 Merge 之前，
看到 MR 動到下面這些路徑就要停下來看清楚。

| 路徑 | 動到它代表什麼 | 看什麼 |
|---|---|---|
| `deploy_exclude.txt` | 動到 rsync 的刪除保護清單 | **漏一行就會在下次部署洗掉正式機的 `.env`**（見 [11_CD_rsync部署機制 · 第 3 節](../進階調整/11_CD_rsync部署機制.md#3-排除清單--刪除保護清單最重要的一節)） |
| `.gitlab-ci.yml` | 動到 pipeline 本身 | 有沒有把檢查關掉（`allow_failure`、改門檻、刪 job） |
| `.gitleaks.toml` | 動到機密偵測規則 | 有沒有把規則放寬到形同虛設 |
| `ci/` | 動到檢查與部署腳本 | 尤其 `build_sbom.sh`、`dtrack_suppress_os.sh` 的放行範圍 |
| `dagster_workspace/dagster_code/table_mapping.py` | 動到會刪資料的設定 | 影響哪些表 |

> 📌 **這幾個路徑的改動，Maintainer 不該「順手就合」。**
> 這是流程規定，系統擋不住 —— CE 就是這樣。
> 真的需要系統強制，就是升級 Premium（見 3-5）。

### 3-5. 升級到 Premium 之後要補什麼

真的需要系統強制核准時，升級 Premium 會多出
`Settings → Merge requests → Merge request approvals` 區塊，屆時補上：

| 設定 | 值 | 擋掉什麼 |
|---|---|---|
| Approvals required | **1**（人手夠設 2） | 至少一位不是作者的人看過 |
| Target branch | `main` | 只對正式分支強制 |
| Eligible approvers | 開發團隊群組（不要指定單一個人） | |
| **Prevent approval by author** | ✅ | 作者自己 approve 自己 |
| **Prevent approvals by users who add commits** | ✅ | 幫忙推過 commit 的人不算獨立審查者 |
| **Prevent editing approval rules in merge requests** | ✅ | 作者在自己 MR 裡把規則改成 0 人 |
| **Remove all approvals when commits are added** | ✅ | ★先拿 approve、再偷偷加 commit★ |

升級後 `main` 的保護分支設定還會多出 **Require approval from code owners**，
搭配 repo 根目錄的 `CODEOWNERS` 檔案，就能讓 3-4 那些高風險路徑
**自動要求指定的人核准**——那時候才不用再靠流程規定。

### 3-6. 現在這幾層加起來的效果（CE）

| 層 | 擋掉什麼 | 系統強制？ |
|---|---|---|
| `Allowed to push and merge = No one` | 完全不可能繞過 MR | ✅ |
| `Pipelines must succeed` | lint／資安掃描沒過就合不了 | ✅ |
| `All threads must be resolved` | reviewer 的問題必須被回應 | ✅ |
| **`Allowed to merge = Maintainers`** | **作者自己合不了，要另一個人動手** | ✅（Maintainer 之間靠自律） |
| 事後抽查 Merged MR | 抓「開了就自己合」 | ❌ 靠流程 |

## 4. 新人加入 / 離職

### 加入

```
1. 確認對方 LDAP 帳號可以登入 GitLab（第一次登入會自動建 GitLab 使用者）
2. 專案 → Manage → Members → Invite members
     dagster-workspace  → Developer
     bcp-scripts        → Developer
3. 請對方做完 03_本地環境設定與提交前檢查.md
4. 請對方先開一個練習 MR（改個註解就好），走完整流程一次
```

**不要**一開始就給 Maintainer。合併到 `main` = 直接推到正式機。

### 離職 / 轉調

```
1. 專案 → Manage → Members → 移除（兩個 repo 都要）
2. 檢查有沒有以他名義建立的 Personal Access Token
     Admin Area → Users → 該使用者 → Impersonation Tokens
3. 如果他曾經是 Maintainer、碰過 CI/CD Variables：
     ★ 輪替所有他看得到的機密 ★
     - DEPLOY_SSH_KEY（見附錄 A 的金鑰輪替）
     - DTRACK_API_KEY
     - 正式 DB 密碼
   Masked 變數在 UI 上看不到值，但 Maintainer 可以改成不 masked，
   或寫一個 job 把它 echo 出來 —— 所以「曾經是 Maintainer」就要當作看過。
4. LDAP 那邊停用帳號（由 IT 處理）
```

## 5. Review 該看什麼

給 reviewer 的檢查重點。**不是看程式碼漂不漂亮，CI 已經管了那部分。**

### 一定要看

| 項目 | 怎麼看 |
|---|---|
| **這個改動會碰到正式資料嗎** | 有沒有動到 `table_mapping.py` 的 `retention_years`、`archive_table`——那些會刪資料 |
| **dbt 模型的 `alias`** | 改 alias = 換一張資料表，下游的匯出設定要跟著改 |
| **有沒有 `# nosec` / gitleaks allowlist** | 有的話理由寫清楚了嗎？寫不清楚就退回 |
| **`.env` 相關** | 有沒有把該進 `.env` 的東西寫死在程式碼裡 |
| **跨 repo 的改動** | 對面那個 MR 開了嗎？順序對嗎（先 VM1 後 VM4）？ |
| **`deploy_exclude.txt` / `.gitignore`** | 新增執行期產物的話，兩份都改了嗎？ |

### 快速放行的情況

| 情況 | 可以快速放行 |
|---|---|
| 標題註明「純格式化」且 diff 全是排版 | ✅ |
| 只改註解 / 文件 | ✅ |
| 新增 dbt 模型，沒有動到既有模型 | ✅（但要確認 `sources.yml` 有登記） |

### 一定要問清楚才放行

| 情況 | 要問什麼 |
|---|---|
| 動到 `assets.py` / `sensors.py` | 影響範圍是全部的表還是特定幾張？ |
| 動到 `dagster.yaml` | 這需要重啟容器，什麼時候重啟？ |
| 刪掉檔案 | 正式機上那份會被 `--delete` 清掉，確定不需要了？ |
| 改 CI/CD 設定 | 會不會讓某個檢查靜默失效？ |

## 6. CI/CD Variables 的權限

只有 **Maintainer 以上**才能看到與修改
（Settings → CI/CD → Variables 這個頁面 Developer 進不去）。

新增變數時的鐵則：

```
[ ] Masked  —— 值不會出現在 job log 裡
[ ] Protected —— 只有保護分支（main）上跑的 job 拿得到
[ ] Environment scope —— production / staging 分開設值
```

三個都要，缺一個就有洞。詳見
[13_Variables與環境隔離](../進階調整/13_Variables與環境隔離.md)。

## 7. 設定完之後驗證一次

```
[ ] 用 Developer 帳號試著 git push origin main       → 應該被拒絕
[ ] 用 Developer 帳號開一個 MR，看得到 Merge 鍵嗎    → 應該是灰的（缺 approval）
[ ] ★ 作者自己按 Approve → 應該按不下去（Prevent approval by author）★
[ ] 找另一個人 approve 後，Merge 鍵才亮起來
[ ] ★ approve 之後再 push 一個 commit → approval 應該被清掉、Merge 鍵重新變灰 ★
[ ] 改 deploy_exclude.txt 開一個 MR → 應該要求 code owner approval
[ ] 讓 CI 故意紅一次，確認 Merge 鍵被鎖住
[ ] 在功能分支上跑一個 echo $DEPLOY_HOST 的 job      → 應該是空的
[ ] 在 main 上跑同一個 job                          → 應該有值（但被遮成 [MASKED]）
[ ] 用 Developer 帳號進 Settings → CI/CD            → 應該看不到 Variables 區塊
```

> 打星號的三項是 EE Approval 機制的核心，**一定要實測**。
> 這三項只要有一項沒生效，「一定要有人 code review」就只是口頭約定而已。
