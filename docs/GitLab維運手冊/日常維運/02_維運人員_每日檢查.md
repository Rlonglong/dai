# 02 · 維運人員 · 每日檢查

每天早上花五分鐘看完這四件事就好。看到紅色時，這份文件會告訴你**這是不是你該處理的**。

> 這份只講 GitLab / CI/CD 這條線。Dagster 的排程狀態請看
> [Dagster維運手冊 · 01_維運人員_每日操作手冊](../../Dagster維運手冊/日常維運/01_維運人員_每日操作手冊.md)。

## 每日四看

| # | 看什麼 | 在哪看 | 紅了要不要立刻處理 |
|---|---|---|---|
| 1 | 昨晚的**雜湊對帳**排程 | 兩個 repo → CI/CD → Pipelines，篩 `Schedules` | **要，最優先** |
| 2 | `main` 分支最近的 **deploy** | 兩個 repo → CI/CD → Pipelines，篩 `main` | 要 |
| 3 | **開著的 MR** 有沒有卡住 | Merge requests → Open | 不用，但要提醒 |
| 4 | GitLab 服務本身 | `https://gitlab.dai.post.gov.tw/-/health` | 要 |

## 1. 雜湊對帳（最重要）

**它在回答**：GitLab 上 `main` 的內容，跟正式機上實際在跑的檔案，還是同一份嗎？

### 綠燈

```
[ OK ]  完整性驗證通過：兩端內容一致（62 73d1815b0144...）
```

沒事，往下一項。

### 紅燈 —— 這是**資安事件**，不是一般的 pipeline 失敗

job log 會直接列出差在哪，分三類：

#### 類型 A：「兩邊都有但內容不同」← 最可疑

```
  ▸ 兩邊都有但內容不同（★最可疑：有人直接改了正式機★）：
      dagster_code/table_mapping.py
```

**代表有人繞過 GitLab，直接在正式機上改了檔案。**

處理步驟：

```bash
# 1. 先把正式機那份抓下來，不要急著覆蓋掉（那是唯一的證據）
ssh gitlab_runner@<VM4_IP>
cp /data/deploy/workspace/dagster_workspace/dagster_code/table_mapping.py \
   /tmp/evidence_$(date +%F).py

# 2. 看是什麼時候被改的
ls -la --time-style=full-iso /data/deploy/workspace/dagster_workspace/dagster_code/

# 3. 對照那個時間點誰登入過
sudo grep "$(date -d '1 day ago' +%b\ %d)" /var/log/secure | grep -i "accepted"
#    集中式的 log 在 VM4 的 /data/log/dai/ 底下
```

然後：

| 情況 | 怎麼處理 |
|---|---|
| 是**緊急修復**還沒補回版控 | 通知那個人**當天**開 MR 補上。補上並合併後對帳就會恢復綠燈 |
| 是**不該有的改動** | 通報資安。重跑 CD job 把正式機拉回一致，證據保留 |
| 是**部署到一半失敗** | 看 2. 的 deploy pipeline 是不是也紅的。重跑 deploy job |

> ⚠️ **不要自己直接重跑 CD job 就當作解決了。**
> `rsync --delete` 會把正式機上那份改動洗掉。如果那是還沒進版控的緊急修復，
> 洗掉就沒了。**一定要先確認那份改動是什麼、要不要留**。

#### 類型 B：「只有 GitLab 有、正式機缺少」

```
  ▸ 只有 GitLab 有、正式機缺少（同步沒完成）：
      dbt_project/models/ATM_K.sql
```

同步沒傳完。看一下 deploy pipeline 是不是紅的，然後**重跑 deploy job** 即可。
這個安全，rsync 是冪等的。

#### 類型 C：「只有正式機有、GitLab 沒有」

```
  ▸ 只有正式機有、GitLab 沒有：
      dbt_project/models/ATM_K_backup_20260801.sql
```

通常是有人在正式機上留了備份檔或臨時檔。確認不需要之後重跑 deploy job 清掉。

如果是**新出現的執行期產物**（某個新功能開始寫檔案到那個目錄），
那是排除清單漏了，要請開發人員同時更新 `deploy_exclude.txt` 和 `.gitignore`。

## 2. deploy pipeline

`main` 分支上最近一次的 pipeline。綠燈代表：

- 程式碼已經同步到正式機
- `chown` 做完了（Dagster 容器讀得到）
- dbt manifest 重產完了
- 部署後的雜湊對帳通過

紅燈的話，看紅在哪一段：

| 紅在 | 意思 | 你能做什麼 |
|---|---|---|
| `SSH 連線失敗` | VM3 連不到目標機 | 檢查目標機是否開機、22 port 通不通。見 [14_疑難排解](../進階調整/14_疑難排解.md) |
| `rsync 失敗` | 傳輸中斷 | 檢查目標機磁碟空間 `df -h`。空間夠的話重跑 job |
| `post-deploy 失敗` | chown 或 dbt parse 出錯 | **程式碼已經推上去了但 manifest 沒更新**。看 log 裡的 dbt 錯誤，通知該 MR 的作者 |
| `雜湊比對不一致` | 同上，見第 1 節 | |

> 📌 **紅在 `post-deploy` 的時候要特別注意**：檔案已經在正式機上了，
> 但 Dagster 還在用舊的 manifest。這時候 Dagster UI 上看到的是舊模型清單，
> 但檔案是新的——這個不一致狀態要盡快處理，不要放著過夜。

## 3. 開著的 MR

不是你的工作，但幫忙看一眼：

| 現象 | 提醒誰 |
|---|---|
| MR 開超過三天沒人 review | 在群組裡 @reviewer |
| MR pipeline 紅了超過一天沒動 | @作者 |
| MR target 是 `main` 但沒有指定 reviewer | @作者，正式環境一定要有人 review |

## 4. GitLab 服務本身

```bash
# 健康檢查
curl -sk -o /dev/null -w "%{http_code}\n" https://gitlab.dai.post.gov.tw/users/sign_in
# 預期：200

# Runner 有沒有在線
# GitLab UI → Admin Area → CI/CD → Runners
# vm3-ci-runner 和 vm3-cd-runner 都要是綠色的 online
```

Runner 離線的話，pipeline 會一直卡在 pending：

```bash
# 在 VM3
docker ps | grep gitlab-runner
docker logs --tail 50 gitlab-runner-cd
docker restart gitlab-runner-cd
```

## 什麼情況要通報

| 情況 | 通報對象 | 急迫性 |
|---|---|---|
| 雜湊對帳出現「兩邊都有但內容不同」，且查不出是誰改的 | 資安 + 系統負責人 | **立即** |
| deploy 紅燈超過兩小時沒人處理 | 系統負責人 | 立即 |
| GitLab 服務起不來 | 系統負責人 | 立即 |
| 有人要求你「直接上機器改一下就好」 | **拒絕，並請對方走 MR**；對方堅持的話通報系統負責人 | — |
| Runner 重啟後還是離線 | 系統負責人 | 當天 |
| MR 卡住 | 群組裡提醒即可 | 當天 |
