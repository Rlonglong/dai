# 01 · 開發人員 · 日常開發流程

從「我要改一支 dbt 模型」到「正式機上跑的是新版」，中間完整經過哪些步驟。

> 第一次使用請先做完 [03_本地環境設定與提交前檢查](./03_本地環境設定與提交前檢查.md)，
> 沒裝 hook 的話你會在 push 到伺服器時才被擋，比較浪費時間。

---

## 0. 先搞清楚你要改的東西在哪個 repo

| 你要改的東西 | repo | 部署到 |
|---|---|---|
| dbt 模型、macro、`sources.yml` | `dagster-workspace` | VM4 |
| `table_mapping.py`、`db_sync/config.py` | `dagster-workspace` | VM4 |
| `assets.py`、`sensors.py`、`dagster.yaml` | `dagster-workspace` | VM4 |
| VM1 的清洗函式 `*_CLEAN.py` | `bcp-scripts` | VM1 |
| VM1 的 `clean_remote.py`、`bcp_remote.py` 等 | `bcp-scripts` | VM1 |
| 檔規 | `bcp-scripts` | VM1 |

兩邊都要改的情況見 [第 7 節](#7-跨-repo-的改動要一起上)。

---

## 1. 開分支

```bash
git checkout main
git pull origin main          # ★一定要先更新，不然等下 MR 會有一堆無關的衝突
git checkout -b feat/add-atm-k-model
```

分支命名慣例：

| 前綴 | 用在 |
|---|---|
| `feat/` | 新增功能（新模型、新資料表、新匯出） |
| `fix/` | 修 bug |
| `chore/` | 不影響行為的整理（格式化、改註解、調 CI） |
| `hotfix/` | 正式機出事，要緊急處理 |

---

## 2. 改東西、commit

```bash
# 改完之後
git add dagster_workspace/dbt_project/models/ATM_K.sql
git commit -m "feat: 新增 ATM_K 異常提領偵測模型"
```

commit 當下 **pre-commit hook** 會跑：

```
================================================================================
 [1/2] 機密資訊防護 (gitleaks --staged)  ★ 不可跳過 ★
================================================================================
[ OK ]  Gitleaks 掃描完畢，未發現金鑰（掃描範圍：已 staged 的變更）。

================================================================================
 [2/2] 靜態掃描與排版檢查 (flake8 / bandit / sqlfluff)
================================================================================
  > 檢查: SQL 語法規範 (sqlfluff)
✅ SQL 語法規範 (sqlfluff) 通過。

語法與資安檢查完畢！
```

被擋了怎麼辦 → [03_本地環境設定與提交前檢查 · 被擋住的時候](./03_本地環境設定與提交前檢查.md#4-被擋住的時候怎麼修)

---

## 3. push

```bash
git push -u origin feat/add-atm-k-model
```

push 當下 **pre-push hook** 會跑，範圍比 pre-commit 大：

| 檢查 | 範圍 | 可跳過？ |
|---|---|---|
| gitleaks | **整批要推出去的 commit** + 工作目錄現況 | ❌ 永遠不行 |
| pip-audit | 有動到 `requirements.txt` 才跑 | ✅ |
| flake8 / bandit / black | 這批 commit 動到的 `.py` | ✅ |
| sqlfluff | 這批 commit 動到的 `.sql` | ✅ |

品質檢查誤判、真的趕時間：

```bash
DAI_SKIP_QUALITY=1 git push      # 只跳過品質檢查，gitleaks 照跑
```

> ⚠️ **`--no-verify` 沒有用。**
> 就算你跳過本地 hook，VM3 的 pre-receive hook 還是會掃同一份規則，
> push 會直接被伺服器拒絕。與其被拒絕，不如在本地修掉。

---

## 4. 開 Merge Request

push 完 GitLab 會在終端機印一個連結，點進去，或到 GitLab UI → Merge requests → New。

| 欄位 | 怎麼填 |
|---|---|
| Source branch | 你的分支 |
| **Target branch** | **`main`**（正式）或 `develop`（只想先上測試機） |
| Title | 跟 commit message 一致就好 |
| Description | **重點：讓 reviewer 三十秒內看懂「改了什麼、為什麼、怎麼驗證」** |
| Assignee | 你自己 |
| Reviewer | **指定一位同事，不能是你自己** |

Description 建議格式：

```markdown
## 改了什麼
新增 ATM_K 模型，偵測「同一帳戶 24 小時內在三個以上不同 ATM 提領」。

## 為什麼
GSS20260801 需求單，風控科要求新增這條規則。

## 怎麼驗證
- [x] 本地 dbt compile 過，編譯後的 SQL 在 SSMS 跑過，2026-07 全月共 143 筆
- [x] sources.yml 已登記用到的來源表
- [ ] 合併後到 Dagster UI Reload，確認資產出現、手動 materialize 一天

## 風險
只新增模型，沒有動到既有模型與匯出，下游不受影響。
```

## 5. 等 CI + Code Review

### CI pipeline

MR 頁面會顯示 pipeline 狀態。**必須全綠才能合併**（`main` 有設這個規則）。

| Job | 在檢查什麼 | 紅了通常是 |
|---|---|---|
| `format-check` | black 排版（只看你動到的檔案） | 跑 `black <檔案>` 就好 |
| `lint-check` | flake8 | 未使用的 import、行太長 |
| `sql-lint` | sqlfluff | 關鍵字大小寫、縮排；`sqlfluff fix` 可自動修 |
| `dbt-parse` | `ref()` 指到不存在的模型、`sources.yml` 沒登記 | 這個最常紅，訊息很直白 |
| `secret-scanning` | gitleaks 全樹 + 全歷史 | 到這裡才紅代表本地 hook 沒裝 |
| `sast-bandit` | Python 資安 | 通常是 `subprocess` 用法 |
| `sca-dtrack` | 套件弱點，**Critical 或 High 就擋** | 升級套件版本，或標記例外（見下） |
| `deploy:staging` | 手動觸發，推到測試機 | — |

> `sca-dtrack` 紅了不一定要升版。job log 最後會印出三條路
> （升級／標記例外／排期處理），完整步驟見
> [弱掃紅燈與 MR 被卡住的解除流程](../../D-Track與Superset手冊/日常維運/04_弱掃紅燈與MR被卡住的解除流程.md)。

### Code Review

**合併進 `main` 一定要有人 review**，這是正式環境的硬性要求，
不是「最好有」。理由很簡單：`main` 一合併就會自動推到正式機，
沒有中間再確認一次的機會。

> ⚠️ **我們用的是 GitLab CE，系統不會強制核准人數。**
> 實際的把關方式是「**你按不到 Merge 鍵**」——`main` 的
> `Allowed to merge` 設成 Maintainers，所以 MR 一定要由系統負責人合併。
> 開完 MR 之後請主動找 reviewer，不要等。
> 機制細節見 [04_帳號_權限_分支保護 · 第 3 節](./04_帳號_權限_分支保護.md#3-code-review-的強制性ce-版)。

Reviewer 該看什麼 → [04_帳號_權限_分支保護 · Review 檢查重點](./04_帳號_權限_分支保護.md#5-review-該看什麼)

被要求修改時：

```bash
# 在同一個分支繼續改
git add -u && git commit -m "review: 依 review 意見調整 XXX"
git push          # MR 會自動更新，pipeline 重跑
```

## 6. 合併之後

合併進 `main` 會自動觸發 `deploy:production`：

```
deploy:production
  ├─ rsync --delete --checksum  →  VM4
  ├─ ssh 執行 dai-post-deploy-vm4.sh
  │     ├─ chown -R 10001:10001
  │     └─ dbt parse（重產 manifest.json）
  └─ 驗雜湊（兩端內容必須一致）
```

**確認 pipeline 綠燈之後**，還有一步要你自己做：

| repo | 合併後你要做什麼 |
|---|---|
| `dagster-workspace` | 到 Dagster UI → **Reload definitions**<br/>改了 `dagster.yaml` / `workspace.yml` 的話要**重啟容器** |
| `bcp-scripts` | 不用做任何事，下次 Dagster 觸發就會用到新版腳本 |

Reload 的操作見
[Dagster維運手冊 · 02_開發人員_UI操作手冊](../../Dagster維運手冊/日常維運/02_開發人員_UI操作手冊.md)。

### 部署失敗了怎麼辦

pipeline 紅在 `deploy:production` 的話，先看紅在哪一段：

| 紅在 | 意思 | 怎麼辦 |
|---|---|---|
| SSH 連線測試 | 連不到目標機 | 通知 GitLab 管理員，見 [14_疑難排解](../進階調整/14_疑難排解.md) |
| rsync | 傳輸失敗 | 通常是磁碟滿或權限。**程式碼可能只推了一半**，修好之後重跑 job |
| post-deploy | chown 或 `dbt parse` 失敗 | 檔案已經推上去了但 manifest 沒重產。看 job log 的 dbt 錯誤訊息 |
| 驗雜湊 | 兩端不一致 | 見 [12_同步完整性稽核](../進階調整/12_同步完整性稽核.md) |

> **重跑 job 是安全的。** rsync 是冪等的，重跑一次會把狀態拉回一致。
> 但如果失敗原因是「程式碼本身有問題」（例如 `dbt parse` 掛掉），
> 重跑不會有幫助，要開新的 MR 修掉。

## 7. 跨 repo 的改動要一起上

「新增一張資料表」這類事情兩個 repo 都要改：

```
bcp-scripts             dagster-workspace
  clean_functions/        table_mapping.py
  T_XXX_CLEAN.py          sources.yml
  clean_remote.py
```

**做法**：

1. 兩邊各開一個分支，**分支名稱取一樣**（例如都叫 `feat/add-t-xxx`），
   方便 reviewer 對照
2. 兩個 MR 的 Description 互相貼對方的連結
3. **先合併 `bcp-scripts`**（VM1 的腳本），**再合併 `dagster-workspace`**

順序很重要：

| 順序 | 結果 |
|---|---|
| ✅ 先 VM1 再 VM4 | Dagster 上線時，它要呼叫的腳本已經在 VM1 上了 |
| ❌ 先 VM4 再 VM1 | Dagster 已經在叫一支 VM1 上還不存在的腳本 → 那張表的 sensor 會一直失敗 |

> 中間的空窗期通常只有幾分鐘，但如果 sensor 剛好在那時候掃到檔案，
> 就會產生一次失敗的 run，還會觸發失敗告警。
> 兩個 MR 之間隔太久的話，建議先把 `dagster-workspace` 那張表的
> sensor 暫時停掉，等兩邊都上完再開。

## 8. 緊急修復（hotfix）

正式機出事、要馬上修的時候，流程**不變**：一樣要開分支、開 MR、要人 review。

差別只在：

- 分支用 `hotfix/` 開頭
- MR 標題加 `[HOTFIX]`
- 用 GitLab 的 `@` 直接標記 reviewer，並在群組裡喊一聲

**不要為了快而直接 push 到 `main`**——推不上去的（保護分支擋著），
而且就算管理員臨時解除保護推了上去，也會跳過 CI 的資安檢查。

真的十萬火急、連 review 都等不到的話：

1. 先在 VM4 / VM1 上直接改檔案讓服務恢復（這是唯一可接受的例外）
2. **當天之內**把同樣的改動走正常 MR 流程補上
3. 補上之前，隔天的雜湊對帳**會紅燈**——這是設計如此，
   它就是在提醒「有一份手改還沒回到版控」

---

## 檢查清單

```
[ ] 從最新的 main 開分支
[ ] 本地 hook 有裝（ci/install_hooks.sh --check）
[ ] commit 過了 pre-commit
[ ] push 過了 pre-push
[ ] MR target 是 main（正式）
[ ] MR description 寫清楚改了什麼、為什麼、怎麼驗證
[ ] 指定了 reviewer（不是自己）
[ ] CI pipeline 全綠
[ ] review 通過
[ ] 合併後 deploy:production 綠燈
[ ] （dagster-workspace）到 UI 做 Reload definitions
[ ] （跨 repo）兩個 MR 都合併了，順序是先 VM1 後 VM4
[ ] 驗證新功能在正式機上真的正常
```
