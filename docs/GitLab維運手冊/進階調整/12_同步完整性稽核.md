# 12 · 同步完整性稽核（雜湊對帳）

**它在回答**：GitLab 上 `main` 的內容，跟正式機上實際在跑的檔案，現在還是同一份嗎？

---

## 1. 什麼時候跑

| 時機 | 誰觸發 | 為什麼要有這一次 |
|---|---|---|
| **部署完當下** | `ci/deploy_rsync.sh` 最後一步 | rsync 傳到一半斷線的話當場就知道，不會讓 Dagster 拿半套程式碼跑一整晚 |
| **每天固定時間** | GitLab 排程 pipeline | 抓「部署完之後才發生」的漂移 —— 最常見的是有人直接 ssh 上正式機改檔案 |
| **隨時手動** | GitLab UI → Run pipeline | 懷疑有人動過正式機的時候 |

---

## 2. 怎麼算

```
                 來源端（VM3 runner）              目標端（VM4 / VM1）
                        │                                │
        ci/sync_manifest.sh                  同一支腳本，用 ssh 送過去執行
                        │                                │
        依 deploy_exclude.txt 過濾            依同一份排除清單過濾
                        │                                │
        每個檔案算 sha256                      每個檔案算 sha256
                        │                                │
        LC_ALL=C 排序                          LC_ALL=C 排序
                        │                                │
        整份清單再算一次 sha256                 整份清單再算一次 sha256
                        └──────────── 比對 ──────────────┘
```

### 三個關鍵設計

| 設計 | 為什麼 |
|---|---|
| **兩端跑同一支腳本**（現送過去，不依賴目標機上的舊版本） | 避免「兩邊用不同版本的規則算出不同答案」的假警報。稽核工具自己誤報，比不做稽核更浪費人力 |
| **排除規則用同一份 `deploy_exclude.txt`** | `.env`、`target/` 這些本來就該不一樣的東西不會誤報 |
| **只比內容，不比 mtime / 權限** | `rsync -a` 會保留 mtime，但 VM4 上 dbt 執行、`chown` 都可能動到 metadata，拿那些來比會一直誤判 |

腳本刻意只用 POSIX 工具（`find` / `sha256sum` / `sort`），
因為它要能在 VM1 / VM4 上以受限的 `gitlab_runner` 身分執行，那邊沒有 Python 生態。

### 輸出格式

```
02a1659031741de5...  dbt_project/models/sources.yml
97ef23ca37b501e8...  dbt_project/profiles.yml.example
...
TOTAL 62 73d1815b01447ffffaa4522f58e7da9ababa8a86ad91ea2a272460fd40982742
```

最後一行的 `TOTAL <檔案數> <整份清單的雜湊>` 就是比對用的指紋。

## 3. 設定每日排程

GitLab UI → 專案 → **Build → Pipeline schedules → New schedule**

| 欄位 | 值 | 說明 |
|---|---|---|
| Description | `每日同步完整性稽核` | |
| Interval Pattern | `0 6 * * *` | **每天 06:00**。要早於當天第一批 Dagster 排程開跑，這樣發現不一致時還來得及處理 |
| Cron timezone | `Asia/Taipei` | |
| Target branch | `main` | 一定要是 main，才拿得到 production 的變數 |
| Variables | （不用加） | `$CI_PIPELINE_SOURCE == "schedule"` 就足以觸發 verify job |
| Activated | ✅ | |

**兩個 repo 都要設。**

排程只會跑 `verify:production`（其他 job 的 rules 沒有 schedule 這條）。
所以不用擔心排程會誤觸發部署。

### 想改成更頻繁

| 頻率 | Cron | 適合 |
|---|---|---|
| 每天一次 | `0 6 * * *` | 預設，夠用 |
| 每 6 小時 | `0 */6 * * *` | 想更早發現手改 |
| 每小時 | `0 * * * *` | 稽核要求嚴格時。注意會產生大量 pipeline 紀錄 |

每次跑大約 10–30 秒（62 個檔案），成本很低。

## 4. 對不上的時候怎麼查

job log 會直接把差異分三類列出來。

### 類型 A：兩邊都有但內容不同 ← 最可疑

```
  ▸ 兩邊都有但內容不同（★最可疑：有人直接改了正式機★）：
      dagster_code/table_mapping.py
```

**這代表有人繞過 GitLab 直接改了正式機。**

```bash
# 1. 先保留證據，不要急著覆蓋
ssh gitlab_runner@<VM4_IP>
cp /data/deploy/workspace/dagster_workspace/dagster_code/table_mapping.py \
   /tmp/evidence_$(date +%F_%H%M).py

# 2. 什麼時候被改的
ls -la --time-style=full-iso /data/deploy/workspace/dagster_workspace/dagster_code/

# 3. 那個時間點誰登入過
sudo grep -i accepted /var/log/secure | tail -50
# 集中式的在 VM4 的 /data/log/dai/ 底下（見 Dagster維運手冊 18_Log分流與資安）

# 4. 差在哪
diff <(git show main:dagster_workspace/dagster_code/table_mapping.py) \
     /tmp/evidence_*.py
```

| 查出來是 | 怎麼處理 |
|---|---|
| 緊急修復還沒補回版控 | 請那個人**當天**開 MR 補上。合併後對帳自動恢復綠燈 |
| 不該有的改動 | 通報資安。保留證據後重跑 CD job 拉回一致 |
| 部署到一半失敗 | 看 deploy pipeline 是不是也紅的。重跑 deploy job |

> ⚠️ **不要一看到紅燈就重跑 CD job 了事。**
> `rsync --delete` 會把正式機上那份改動洗掉。
> 如果那是還沒進版控的緊急修復，洗掉就沒了。

### 類型 B：只有 GitLab 有、正式機缺少

同步沒傳完。重跑 deploy job 即可（rsync 冪等，安全）。

### 類型 C：只有正式機有、GitLab 沒有

```
  ▸ 只有正式機有、GitLab 沒有：
      dbt_project/models/ATM_K_backup_20260801.sql
```

| 是什麼 | 怎麼處理 |
|---|---|
| 有人留的備份檔 / 臨時檔 | 確認不需要之後重跑 deploy job 清掉 |
| **新出現的執行期產物** | 排除清單漏了。同時更新 `deploy_exclude.txt` 和 `.gitignore` |

## 5. 這套稽核守不住什麼

誠實列出來，免得誤以為有了它就萬無一失：

| 守不住 | 為什麼 | 補償措施 |
|---|---|---|
| **改完又改回去** | 對帳時已經一致了 | 檔案系統稽核（auditd）、rsyslog 的 ssh 登入紀錄 |
| **被排除的檔案被竄改** | `.env`、`target/` 本來就不比對 | 那些檔案靠權限控管（600、只有服務帳號可讀） |
| **`main` 分支本身被塞壞東西** | 對帳只驗「一不一致」，不驗「內容對不對」 | code review + gitleaks + bandit |
| **兩端同時被改成一樣的壞東西** | 需要同時拿到 GitLab 與正式機的權限 | 已經是整條信任鏈被攻破的情境 |
| **對帳期間的空窗** | 每天只跑一次，中間 24 小時看不到 | 提高頻率；或加 auditd 即時告警 |

## 6. 稽核紀錄留在哪

`ci/lib.sh` 的 log 函式會把每次結果送一份到 rsyslog：

```
tag      : dai/gitlab-sync
格式     : DAI|<LEVEL>|<專案>|<commit>|<訊息>
```

依照現有的 log 架構（見
[Dagster維運手冊 · 18_Log分流與資安](../../Dagster維運手冊/進階調整/18_Log分流與資安.md)），
這些會被集中到 **VM4 的 `/data/log/dai/`**，並被每日的 `log_hash.sh` 納入雜湊存證。

所以「某天的對帳結果是什麼」有不可否認的紀錄，可以用來回答稽核問題。

查詢：

```bash
# 在 VM4
sudo grep 'dai/gitlab-sync' /data/log/dai/vm3-*/*.log | tail -20
```

## 7. 手動跑一次

懷疑正式機被動過，不想等排程：

```
GitLab UI → 專案 → Build → Pipelines → Run pipeline
  Branch: main
  → 執行後在 verify stage 手動點 verify:production
```

或在 VM3 的 runner 上直接跑（需要有那些環境變數）：

```bash
export DEPLOY_HOST=<VM4_IP> DEPLOY_USER=gitlab_runner
export DEPLOY_PATH=/data/deploy/workspace/dagster_workspace
export DEPLOY_SSH_KEY=/home/gitlab_runner/.ssh/gitlab_to_vm4
export DEPLOY_KNOWN_HOSTS=/home/gitlab_runner/.ssh/known_hosts
export SOURCE_DIR=dagster_workspace
ci/verify_sync.sh
```
