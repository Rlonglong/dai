# Dependency-Track 備援與復原文件（Docker Compose 部署）

**適用範圍**：本文件適用於以 Docker Compose 部署的 OWASP Dependency-Track 容器，隸屬 nexflow/DAI 多 VM 架構中的 VM3（與 GitLab EE 同一台）。
**架構前提**：Dependency-Track metadata DB 使用共用 Postgres 容器 `infra-db`（volume: `infra-db-data`），資料庫名稱 `dtrack`，使用者 `dt_user`，與其他元件共用同一個 Postgres instance、各自獨立 DB/user。版本 4.14.3。
**維護者**：CY
**最後更新**：2026-08-05

> ⚠️ **版本提醒**：Dependency-Track 於 2026 年 6 月發布 v5.0（代號 Hyades），架構從單一 API server 大幅改為分散式架構（水平擴展、容錯），連帶備份策略會完全不同。v4.x 分支 EOL 訂在 2026-12-09。你們目前的 4.14.3 屬於 v4 架構，本文件內容僅適用於 v4；未來升級到 v5 時，本文件需要整份重寫，不是修修改改可以沿用的。

## 1. 備份策略總覽

### 1.1 與 Keycloak 的關鍵差異

Keycloak 的 token 簽章金鑰存在資料庫裡，`pg_dump` 本身自足。Dependency-Track **不是**這樣——它會將機敏設定（例如外部服務的存取權杖：LDAP bind 密碼、SMTP 密碼、Slack/Jira 等通知整合的 webhook 憑證、外部弱點資料來源的 API token）以 AES256 加密後存進資料庫，而**加密用的金鑰是獨立檔案**，容器化部署預設放在：

```
/data/.dependency-track/keys/secret.key
```

這個模式跟 GitLab 的 `gitlab-secrets.json`、Superset 的 `SECRET_KEY` 是同一類風險：**DB 備份救回來了，但少了這把 key，前述加密欄位一樣解不開**，需要重新設定那幾項整合憑證。差別在於影響範圍比 Superset 小——只有「外部整合的機密欄位」會失效，不會像 Superset 那樣波及所有使用者 session 或連線密碼。

### 1.2 沒有內建的「一鍵匯出」工具

跟 Keycloak 的 realm export、Superset 的 `export-assets` 不同，Dependency-Track 沒有單一指令能把 project、policy、team、notification 設定整包匯出成人類可讀格式。REST API 是以資源為單位（project、policy、team、configProperty、notification publisher/rule 等）個別存取，若要做版控用的可讀快照，需要自行寫腳本逐一呼叫組合。且如同其他工具的 partial export，API 回傳的機敏欄位（如 notification publisher 內的密碼）通常會被遮罩或不完整回傳，所以這條路徑同樣只能當**輔助的版控稽核層**，不能取代 DB 備份作為復原依據。

### 1.3 職責分工

| 項目 | 備份方式 | 負責單位 |
|---|---|---|
| VM 主機層級（磁碟快照） | 定期主機備份 | 公司 VM 管理團隊 |
| `infra-db-data` volume 整體快照 | 隨 VM 快照涵蓋，但**不建議**作為唯一復原手段（同 Superset/Keycloak 文件理由） | 公司 VM 管理團隊 |
| `dtrack` DB（project、component、policy、team、vulnerability 分析結果、notification 設定等） | `pg_dump` 邏輯備份，僅針對此單一 DB | 本文件範圍 |
| `secret.key`（外部整合機密的加密金鑰） | 檔案備份，**關鍵機密** | 本文件範圍 |
| VM3 共用環境變數檔（DB 連線設定等，命名推測為 `vm3.env`，比照 VM5 慣例） | 檔案備份 | 本文件範圍，需你確認實際檔名與路徑 |
| Project/Policy 人類可讀快照 | 自寫腳本打 REST API + GitLab 版控 | 本文件範圍（選用） |

> ⚠️ 這份文件裡涉及 VM3 共用環境變數檔的部分，我先假設你們沿用跟 VM5（`vm5.env`）一致的命名慣例，寫成 `vm3.env`。請確認實際檔名，若不同我再修正。

## 2. 資料實際存放位置

### 2.1 確認 Volume 掛載

```bash
docker inspect dependency-track --format '{{ range .Mounts }}{{ .Source }} -> {{ .Destination }}{{ "\n" }}{{ end }}'
```

### 2.2 典型掛載結構

```yaml
services:
  dependency-track-apiserver:
    image: dependencytrack/apiserver:4.14.3
    env_file:
      - ../env/vm3.env
    environment:
      - ALPINE_DATABASE_URL=${ALPINE_DATABASE_URL}
      - ALPINE_DATABASE_USERNAME=${ALPINE_DATABASE_USERNAME}
      - ALPINE_DATABASE_PASSWORD=${ALPINE_DATABASE_PASSWORD}
    volumes:
      - dtrack-data:/data

  dependency-track-frontend:
    image: dependencytrack/frontend:latest
    environment:
      - API_BASE_URL=http://dependency-track-apiserver:8080
```

> 請對照你實際的 compose 檔案確認變數名稱，Dependency-Track（Alpine 框架）慣用 `ALPINE_DATABASE_*` 前綴的環境變數名稱來設定資料庫連線，若你們的命名不同麻煩告訴我。

### 2.3 重點路徑與位置

| 項目 | 位置 | 備註 |
|---|---|---|
| Metadata DB 實際資料 | `infra-db-data` volume → `infra-db` container 內 `/var/lib/postgresql/data`，DB 名稱 `dtrack` | 多元件共用，**不可**直接檔案層級複製當備份 |
| `secret.key` | container 內 `/data/.dependency-track/keys/secret.key`，對應 host 端掛載的 `dtrack-data` volume | **關鍵機密，需獨立備份** |
| DB 連線設定等環境變數 | `../env/vm3.env`（待確認實際檔名） | VM3 共用，可能也被 GitLab 使用（需確認是否共用同一份） |
| Search index / 暫存資料 | container 內 `/data` 下其他子目錄（Lucene index 等） | 屬於可重建的衍生資料，**不需要**備份，資料庫還原後會自動重新建立 |

> ⚠️ 確認事項：`secret.key` 是在首次啟動時自動產生的，若你們容器重建過、`dtrack-data` volume 沒有正確持久化，這把 key 可能已經換過好幾輪。建議先確認目前 `secret.key` 的檔案時間戳記，跟你們容器/volume 的建立時間比對，確保現在備份的是「當前 DB 裡加密資料實際對應」的那一把，而不是某次容器重建後產生的新版本卻搭配舊的 DB 備份。

## 3. 日常備份操作

### 3.1 Metadata DB 邏輯備份（僅針對 `dtrack` DB）

```bash
docker exec -t infra-db pg_dump -U dt_user -d dtrack -F c \
  -f /tmp/dtrack_db_$(date +%Y%m%d).dump

docker cp infra-db:/tmp/dtrack_db_$(date +%Y%m%d).dump ./dtrack-backup/
docker exec -t infra-db rm /tmp/dtrack_db_$(date +%Y%m%d).dump
```

此指令執行期間不需要停機。

### 3.2 `secret.key` 備份

```bash
docker cp dependency-track-apiserver:/data/.dependency-track/keys/secret.key \
  ./dtrack-backup/secret.key
```

> 建議將 `secret.key` 加密後存放，或至少確保存放位置的存取權限與 `gitlab-secrets.json`、Superset 的 `vm5.env` 同等級管控。

### 3.3 VM3 共用環境變數檔備份

```bash
cp /path/to/compose-project/env/vm3.env ./dtrack-backup/vm3.env
```

> 待確認：若 `vm3.env` 也被 GitLab 共用，這份備份可能已經在 GitLab 備援文件的排程裡處理過，不需要重複建立（同 Superset/Keycloak 文件之間的關係）。請確認後我再調整措辭，避免兩份文件各自重複維護。

### 3.4 人類可讀 Project/Policy 快照（選用，建議搭配 GitLab 版控）

以 Dependency-Track REST API 為基礎，寫一支排程腳本抓取以下資源，組合成 JSON 存檔：

- `GET /api/v1/project` — 專案清單與 metadata
- `GET /api/v1/policy` — policy 清單與條件設定
- `GET /api/v1/team` — team 與權限設定（ACL）
- `GET /api/v1/user` — 使用者清單（managed/LDAP/OIDC，不含密碼）
- `GET /api/v1/notification/rule` — 通知規則設定

```bash
API_KEY="<具備 VIEW_PORTFOLIO 等對應權限的 API Key>"
BASE_URL="http://dependency-track-apiserver:8080/api/v1"

for endpoint in project policy team user notification/rule; do
  curl -s -H "X-Api-Key: $API_KEY" "$BASE_URL/$endpoint" \
    -o "./dtrack-backup/snapshot_${endpoint//\//_}_$(date +%Y%m%d).json"
done
```

這份快照可以 commit 進 GitLab，用 `git diff` 追蹤 project/policy 設定的變更歷程，適合做**設定變更稽核**，不作為完整復原的唯一依據。

### 3.5 備份存放建議

- `dtrack_db` dump + `secret.key` + `vm3.env`，三者須綁在一起保存並視為一組，缺一則整組備份失去復原意義。
- 建議排程頻率：每日一次，重大 policy/project 設定異動後手動加做一次。
- 3.4 節快照可依 commit 頻率決定執行時機。

## 4. 復原演練程序

### 4.1 演練原則

- 於獨立測試環境進行，**不可**復用正式 `infra-db` container。
- 測試用 Postgres container 只需初始化 `dt_user` / `dtrack`。
- Dependency-Track（4.x，基於 Liquibase）啟動時會自動偵測並執行 DB schema migration，不需額外指令，但仍建議測試用 image 版本與正式站一致（4.14.3）。

### 4.2 演練步驟

**Step 1：於正式站建立演練用備份**

```bash
docker exec -t infra-db pg_dump -U dt_user -d dtrack -F c \
  -f /tmp/drill_dtrack_$(date +%Y%m%d).dump
docker cp infra-db:/tmp/drill_dtrack_$(date +%Y%m%d).dump ./drill-config/
docker cp dependency-track-apiserver:/data/.dependency-track/keys/secret.key \
  ./drill-config/secret.key
cp /path/to/compose-project/env/vm3.env ./drill-config/vm3.env
```

**Step 2：建立獨立測試用 Postgres container**

```sql
CREATE USER dt_user WITH PASSWORD '<與正式站對齊或測試用密碼>';
CREATE DATABASE dtrack OWNER dt_user;
```

**Step 3：還原 metadata DB**

```bash
docker cp ./drill-config/drill_dtrack_20260805.dump new-infra-db:/tmp/
docker exec -it new-infra-db pg_restore -U dt_user -d dtrack \
  --clean --if-exists /tmp/drill_dtrack_20260805.dump
```

**Step 4：建立測試用 Dependency-Track container，還原 `secret.key`**

```bash
docker cp ./drill-config/secret.key \
  new-dependency-track:/data/.dependency-track/keys/secret.key
```

啟動 `new-dependency-track` container 時，`env_file` 指向演練用的 `vm3.env`，並將資料庫連線指向 `new-infra-db` 上的 `dtrack`。容器啟動時會自動執行 schema migration。

> ⚠️ `secret.key` 務必在容器**第一次啟動前**就放好。如果容器已經先啟動過一次、自動產生了新的 `secret.key`，之後才把備份的舊 key 蓋上去，可能造成 key 版本混亂，導致部分加密欄位解密異常。

**Step 5：重啟並驗證**

登入 Web 介面，逐項確認：

- [ ] Project 清單與 component 資料是否完整
- [ ] Policy 設定與條件是否存在，且能正常評估（可觸發一次 policy 評估測試）
- [ ] Team／使用者權限（ACL）是否正確
- [ ] LDAP 登入是否正常（間接驗證 `secret.key` 對應正確，因為 LDAP bind 密碼是加密欄位之一）
- [ ] Notification rule 設定是否存在，若有設定外部整合（Slack/Jira/SMTP），該整合是否能正常運作（同樣驗證 `secret.key`）
- [ ] GitLab CI 上傳 SBOM 到 Dependency-Track 的流程是否能正常運作（驗證 API Key 相關權限與 CI 整合是否完整還原）

### 4.3 演練紀錄表（建議每次演練填寫）

| 演練日期 | 備份檔版本 | 還原耗時 | secret.key 驗證結果 | 驗證結果 | 問題紀錄 |
