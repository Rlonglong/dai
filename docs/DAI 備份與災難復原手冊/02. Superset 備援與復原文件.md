# Superset 備援與復原文件（Docker Compose 部署）

**適用範圍**：本文件適用於以 Docker Compose 部署的 Apache Superset 容器，隸屬 DAI 架構中的 VM5。
**架構前提**：Superset metadata DB 使用共用 Postgres 容器 `infra-db`（volume: `infra-db-data`），資料庫名稱 `superset_db`，使用者 `superset_user`，與其他元件（如 Keycloak）共用同一個 Postgres instance、各自獨立 DB/user。
**維護者**：CY
**最後更新**：2026-08-04

---

## 1. 備份策略總覽

### 1.1 備份策略

Superset 幾乎所有核心資產都是輕量、結構化資料（dashboard 定義、chart、dataset、連線設定），適合走「**資料庫邏輯備份 + 人類可讀資產匯出 + 版控**」路線，與現行 Dagster 的作法一致。

### 1.2 職責分工

| 項目 | 備份方式 | 負責單位 |
|---|---|---|
| VM 主機層級（磁碟快照） | 定期主機備份 | 公司 VM 管理團隊 |
| `infra-db-data` volume 整體快照 | 隨 VM 快照涵蓋，但**不建議**作為唯一復原手段（見 1.3） | 公司 VM 管理團隊 |
| `superset_db`（metadata：dashboard、chart、dataset、連線設定、user/role、alert/report） | `pg_dump` 邏輯備份，僅針對此單一 DB | 本文件範圍 |
| `SECRET_KEY` | 檔案/環境變數備份 | 本文件範圍 |
| `superset_config.py` | 檔案備份 | 本文件範圍 |
| 資產人類可讀版本（dashboard/chart/dataset YAML） | `superset export-assets` + GitLab 版控 | 本文件範圍 |

### 1.3 為什麼要單獨對 `superset_db` 做邏輯備份，而不是整個 `infra-db` volume

`infra-db` 是**多元件共用**的 Postgres instance，`infra-db-data` volume 快照會把所有共用此 instance 的元件資料綁在一起。這帶來兩個問題：

1. **復原範圍過大**：若只是 Superset 出問題想單獨復原，用整個 volume 快照會連帶影響其他元件的資料庫狀態，無法做到單一元件的精準復原。
2. **演練與正式環境耦合**：要單獨演練 Superset 復原，不應該連帶起整個 `infra-db` 的所有 DB。

因此本文件採用 `pg_dump -d superset_db` 的方式，只針對 Superset 自己的 DB 做邏輯備份，與其他共用同一 Postgres instance 的元件（如 Keycloak）互不影響，各自獨立備份、獨立演練。

### 1.4 `SECRET_KEY` 的重要性（等同 GitLab 的 `gitlab-secrets.json`）

Superset 用 `SECRET_KEY` 做兩件事：
- Flask session 簽章與 CSRF 保護
- 加密 metadata DB 裡儲存的**外部資料庫連線密碼**（例如用 `pymssql` 接的 MS SQL 帳密）

若 `SECRET_KEY` 遺失，或還原後的 metadata DB 與新的 `SECRET_KEY` 不一致，會導致：
- 所有透過 UI 設定的資料庫連線密碼**無法解密**，需要重新輸入
- 所有使用者 session 全部失效，需要重新登入

> 目前確認版本為 Superset 6.1，已遠高於 2.1（自 2.1.0 起 `SECRET_KEY` 為必填項目，且加密機制已整合進 `SECRET_KEY`，不存在獨立的 Fernet key），因此本文件只需處理 `SECRET_KEY` 即可，無需額外處理舊版的 Fernet key 設定。

## 2. 資料實際存放位置

### 2.1 確認 Volume 掛載

執行前務必先確認實際的 docker-compose 掛載設定：

```bash
docker inspect superset --format '{{ range .Mounts }}{{ .Source }} -> {{ .Destination }}{{ "\n" }}{{ end }}'
docker inspect infra-db --format '{{ range .Mounts }}{{ .Source }} -> {{ .Destination }}{{ "\n" }}{{ end }}'
```

### 2.2 典型掛載結構（依實際確認結果）

```yaml
services:
  superset:
    env_file:
      - ../env/vm5.env
    environment:
      - DB_HOST=${VM4_IP}
      - SUPERSET_CONFIG_PATH=/app/superset_config.py
    volumes:
      - ./superset/superset_config.py:/app/superset_config.py
      - ./superset/superset_home:/app/superset_home

  infra-db:
    image: postgres:<version>
    volumes:
      - infra-db-data:/var/lib/postgresql/data
```

### 2.3 重點路徑與位置

| 項目                             | 位置                                                                                                                                                      | 備註                                                                                                                |
| -------------------------------- |:--------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Metadata DB 實際資料             | `infra-db-data` volume → `infra-db` container 內 `/var/lib/postgresql/data`                                                                               | 多元件共用，**不可**直接檔案層級複製當備份                                                                          |
| `superset_config.py`             | host 端掛載路徑（依實際 compose 設定）                                                                                                                    | 主設定檔，含 Keycloak OIDC client_id/secret、`SQLALCHEMY_DATABASE_URI` 等                                           |
| `custom_sso_security_manager.py` | host 端掛載路徑（依實際 compose 設定）                                                                                                                    | 用於解析 Keycloak 回傳內容                                                                                                                    |
| `SECRET_KEY`                     | 實際值定義於 `../env/vm5.env`（透過 docker-compose `env_file` 機制載入），`superset_config.py` 內僅用 `os.getenv("SUPERSET_SECRET_KEY")` 讀取，本身不含值 | **關鍵機密，需獨立備份，備份對象是 `vm5.env`，不是 `superset_config.py`；且此檔案可能為 VM5 多元件共用，見 2.4 節** |
| `superset_home`                  | container 內 `/app/superset_home`                                                                                                                         | 快取、上傳的 logo 等，非核心，可不備份                                                                              |


### 2.4 `SECRET_KEY` 的實際設定方式（已確認）

本環境的設定方式為：`superset_config.py` 內以 `os.getenv("SUPERSET_SECRET_KEY")` 讀取值，容器透過 docker-compose 的 `env_file` 機制載入 `../env/vm5.env`（相對於 compose 檔案的路徑），`SUPERSET_SECRET_KEY` 實際定義在這份檔案裡，不需要在 `environment:` 區塊重複宣告。

驗證備份的檔案內容與容器實際套用的值一致：

```bash
grep SUPERSET_SECRET_KEY /path/to/compose-project/env/vm5.env
docker exec -it superset env | grep SUPERSET_SECRET_KEY
```
- `superset_config.py` 本身不含機密內容，可以正常隨 GitLab 版控。
- 真正需要備份的機密是 `vm5.env`，這才是容器重建後能否還原出同一把 `SECRET_KEY` 的關鍵，且很可能同時也是其他 VM5 元件復原時需要的檔案。

## 3. 日常備份操作

### 3.1 Metadata DB 邏輯備份（僅針對 `superset_db`）

```bash
docker exec -t infra-db pg_dump -U superset_user -d superset_db -F c \
  -f /tmp/superset_db_$(date +%Y%m%d).dump

docker cp infra-db:/tmp/superset_db_$(date +%Y%m%d).dump ./superset-backup/
docker exec -t infra-db rm /tmp/superset_db_$(date +%Y%m%d).dump
```

使用 `-F c`（custom format）而非純文字 SQL，可支援後續 `pg_restore` 做選擇性還原，且檔案較小。

### 3.2 關鍵機密與設定檔備份

```bash
# superset_config.py, custom_sso_security_manager.py本身不含機密（僅 os.getenv 讀取邏輯），可正常隨 GitLab 版控
docker cp superset:/app/superset_config.py ./superset-backup/
docker cp superset:/app/custom_sso_security_manager.py ./superset-backup/

# 真正的機密來源是 vm5.env，直接從 compose 專案目錄複製
cp /path/to/compose-project/env/vm5.env ./superset-backup/vm5.env

# 驗證：確認備份的 vm5.env 內容與容器實際套用的值一致
docker exec -it superset env | grep SUPERSET_SECRET_KEY
```

> `/path/to/compose-project/env/vm5.env` 請換成實際的路徑。由於環境變數檔是以 VM 為單位，其機密性最高，需要額外加密存放，且必須加入 `.gitignore`。
>
> 建議將 `vm5.env` 加密後存放，或至少確保存放位置的存取權限與 `gitlab-secrets.json` 同等級管控，不可與一般設定檔混放於權限寬鬆的目錄。。

### 3.3 人類可讀資產匯出（選用，建議搭配 GitLab 版控）

Superset 內建 CLI 可將 dashboard、chart、dataset、資料庫連線定義（不含密碼明文）匯出成一包 YAML：

```bash
docker exec -t superset superset export-assets -f /tmp/superset_assets_$(date +%Y%m%d).zip
docker cp superset:/tmp/superset_assets_$(date +%Y%m%d).zip ./superset-backup/
docker exec -t superset rm /tmp/superset_assets_$(date +%Y%m%d).zip
```

這份 YAML 包可以直接 commit 進 GitLab repo，用 `git diff` 追蹤 dashboard/chart 的變更歷程，作法概念上與你現行 Dagster 用 `.py` 檔案版控的邏輯一致，比單純的二進位 DB dump 更適合做**設定變更稽核**。

> 注意：`export-assets` 匯出的資料庫連線定義不含明文密碼，還原後需要重新填入密碼，或透過對應 metadata DB 還原取得（見 4.2 差異說明）。

### 3.4 備份存放建議

- Superset 備份總體涵蓋以下四個組件: `superset_db.dump` + `superset_config.py` + `custom_sso_security_manager.py` + `vm5.env`。其中 `vm5.env` 是機密等級最高的一份，因為它含有 `SUPERSET_SECRET_KEY` 實際值，且可能同時涵蓋其他 VM5 元件的機密。
- 建議存放至與主機分開的隔離區，並比照機密等級管控存取權限。
- 建議排程頻率：每月一次，另外在重大 dashboard/連線設定異動後手動加做一次。
- `export-assets` 的 YAML 包可依 commit 頻率決定，例如每次有明顯資產異動時執行並 commit。

## 4. 復原演練程序

### 4.1 演練原則

- 於獨立測試環境進行，**不可**復用正式 `infra-db` container，避免影響其他共用此 Postgres instance 的元件（如 Keycloak）。
- 測試用 Postgres container 只需初始化 `superset_user` / `superset_db`，不需要完整複製其他元件的 DB。
- Superset image 版本須與正式站一致，metadata schema 版本不符可能導致還原後執行 migration 失敗。

### 4.2 兩種復原方式的差異

| 方式 | 還原範圍 | 適用情境 |
|---|---|---|
| `pg_restore`（DB dump 還原） | 完整還原，含連線密碼明文（透過 SECRET_KEY 解密） | 完整災難復原，效果等同回到備份當下的完整狀態 |
| `import-assets`（YAML 資產匯入） | dashboard/chart/dataset 定義，**不含**連線密碼 | 單純想復原某幾個 dashboard 誤刪/誤改，不影響其他資料 |

正式的復原演練建議以 `pg_restore` 路徑為主，`import-assets` 作為輔助驗證。

### 4.3 演練步驟（以 `pg_restore` 完整復原為主）

**Step 1：於正式站建立演練用備份**

```bash
docker exec -t infra-db pg_dump -U superset_user -d superset_db -F c \
  -f /tmp/drill_superset_$(date +%Y%m%d).dump
docker cp infra-db:/tmp/drill_superset_$(date +%Y%m%d).dump ./drill-config/
docker cp superset:/app/superset_config.py ./drill-config/
cp /path/to/compose-project/env/vm5.env ./drill-config/vm5.env
```

**Step 2：建立獨立測試用 Postgres container**

啟動全新、乾淨 volume 的測試 Postgres container，並初始化與正式站相同的 role/database：

```sql
CREATE USER superset_user WITH PASSWORD '<與正式站對齊或測試用密碼>';
CREATE DATABASE superset_db OWNER superset_user;
```

**Step 3：還原 metadata DB**

```bash
docker cp ./drill-config/drill_superset_20260804.dump new-infra-db:/tmp/
docker exec -it new-infra-db pg_restore -U superset_user -d superset_db \
  --clean --if-exists /tmp/drill_superset_20260804.dump
```

**Step 4：建立測試用 Superset container，還原設定檔與 `vm5.env`**

```bash
docker cp ./drill-config/superset_config.py new-superset:/app/superset_config.py
```

由於 `vm5.env` 可能同時包含 Keycloak、Nginx 等其他 VM5 元件的機密，若演練環境的權限控管不到位，**不建議整份搬進測試環境**。建議以下二選一：

- **方式 A（環境可信任）**：直接將 `vm5.env` 整份放入演練用的 `env_file` 路徑，與正式站相同的 `env_file` 機制自動載入。
- **方式 B（僅想驗證 Superset 部分，環境不完全可信）**：只抽取 Superset 相關的變數，另外組一份精簡版：
  ```bash
  grep -E "SUPERSET_SECRET_KEY|DB_HOST" ./drill-config/vm5.env > ./drill-config/vm5-superset-only.env
  ```
  再將這份精簡版放入演練環境的 `env_file` 路徑。

啟動 `new-superset` container 時，務必確認容器實際取得的 `SUPERSET_SECRET_KEY` 與正式站**同一組**，並將 `SQLALCHEMY_DATABASE_URI`／`DB_HOST` 指向 `new-infra-db`。由於 `superset_config.py` 是用 `os.getenv()` 讀取，只要對應的 env 檔案正確載入，容器啟動時會自動取得正確的值，不需要額外手動比對或設定。

> ⚠️ 這一步是整個演練最容易出錯的地方：`SECRET_KEY` 若與原本產生 metadata DB 時的值不同，即使 DB 還原成功，所有連線密碼欄位仍會解密失敗。務必確認演練用的 `vm5.env` 是從正式站**當下**複製，而不是舊版或別份殘留的檔案。

**Step 5：執行 DB migration（若版本間有 schema 差異）**

```bash
docker exec -it new-superset superset db upgrade
```

**Step 6：重啟並驗證**

```bash
docker exec -it new-superset superset init
```

登入 Web 介面，逐項確認：

- [ ] Dashboard 清單與內容是否完整
- [ ] Chart 是否正常渲染（間接驗證 dataset 對應的資料庫連線是否正常）
- [ ] 資料庫連線設定是否存在，且密碼可正常解密連線成功（驗證 `SECRET_KEY` 對應正確）
- [ ] User/Role 權限是否正確
- [ ] Keycloak OIDC SSO 登入是否正常（驗證 `superset_config.py` 還原正確）
- [ ] Alert/Report 排程設定是否存在
