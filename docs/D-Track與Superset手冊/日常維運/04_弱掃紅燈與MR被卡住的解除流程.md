# 04 · 弱掃紅燈與 MR 被卡住的解除流程

> 這份文件在回答：**掃出弱點、pipeline 紅燈、東西上不去，現在該做什麼。**
> 從「先搞清楚是哪一種紅燈」開始，一步一步做到綠燈。

---

## 1. 先分清楚是哪一種紅燈

**這一步不要跳過。** 兩種紅燈的影響範圍完全不同，處理的急迫性也不同。

| | A. MR 的 `sca-dtrack` 紅了 | B. 每季 `sca-dtrack-quarterly` 紅了 |
|---|---|---|
| 在哪裡看到 | 你自己開的 MR 頁面 | GitLab → Build → Pipelines，`main` 上一條排程 pipeline |
| 觸發來源 | merge request / push | 排程（1/4/7/10 月 1 號 03:00）或手動 |
| 擋門標準 | **Critical > 0** | **Critical 或 High > 0** |
| 直接後果 | **這個 MR 合併不了** | `main` 上出現紅燈紀錄 |
| 對其他人的影響 | 只影響你這個 MR | 不會擋住別人的 MR |

### ⚠️ 一個常見誤解要先講清楚

> **每季弱掃掃出 High，並不會直接把所有人的 MR 鎖起來。**

原因是兩個 job 的觸發條件互斥（寫在 `.gitlab-ci.yml` 的 `rules` 裡）：

- `sca-dtrack`：只在 merge request / push / main 上跑，**門檻只有 Critical**
- `sca-dtrack-quarterly`：只在 `SCHEDULE_TYPE == "quarterly"` 的排程與手動觸發時跑，
  才會帶 `DTRACK_FAIL_ON_HIGH=1`

所以每季掃出 High 之後，**開新 MR 還是會綠燈**（除非同時有 Critical）。

**但它仍然必須處理**，因為：

1. `main` 上留著一條紅燈紀錄，稽核會問
2. 團隊如果有「main 不能有紅燈才可以出版本」的規定，實務上就是被卡住
3. 今天的 High，下個月可能被重新評為 Critical——那時候就是真的全員卡住

**如果你們希望 High 也要擋 MR**（讓紀律更嚴），做法見
[進階調整 · 10](../進階調整/10_D-Track_專案_API_Key_與擋門門檻.md#3-調整擋門門檻)。

## 2. 通用解除流程（四步）

```
① 看懂是什麼      → job log 的連結點進 D-Track，確認套件、CVE、嚴重度
② 決定怎麼處理    → 升級版本 ／ 標記例外 ／ 排期處理
③ 讓 D-Track 重算 → 標記完要 Refresh Metrics，數字才會變
④ 重跑 job 確認   → Retry job，看到 [OK] 才算解除
```

**③ 最容易被漏掉**：在 D-Track 網頁上標記完例外，pipeline 重跑還是紅的，
八成就是 metrics 還沒重算。詳見第 5 節。

---

## 3. ① 看懂是什麼

Job log 長這樣：

```
=======================================
🛡️  資安掃描結果（bcp-scripts:main）
🔥 Critical : 1
🚨 High     : 3
⚠️  Medium   : 7
ℹ️  Low      : 12
   D-Track  : https://dtrack.dai.post.gov.tw/projects/a3f2b91c-...
=======================================
[FAIL]  偵測到 1 個 Critical 弱點 → 阻擋 Pipeline
```

點那個 D-Track 連結，進到該專案的 **Vulnerabilities** 分頁。

要看的四個欄位：

| 欄位 | 你要從它得到什麼 |
|---|---|
| **Component** | 是哪個套件、目前用哪一版 |
| **Vulnerability** | CVE 編號，點進去有完整說明 |
| **Severity** | Critical / High / Medium / Low |
| **Fixed in**（在 CVE 詳情裡） | **有沒有修好的版本可以升**——這決定了下一步走哪條路 |

> 📸 **待補截圖**：D-Track 專案的 Vulnerabilities 分頁，
> 標出上面四個欄位的位置。

## 4. ② 決定怎麼處理

```
                有沒有修補版本？
                 │           │
                有           沒有
                 │           │
        升級會不會壞？        我們有沒有用到那個弱點功能？
         │        │            │            │
        不會      會           沒用到        有用到
         │        │            │            │
      ★路線A★  ★路線C★     ★路線B★      ★路線C★
      直接升級  排期處理     標記例外      排期處理／緊急放行
```

### 路線 A：升級套件版本（**正解，優先走這條**）

只有 `bcp-scripts` 走 `requirements.txt`；`dagster-workspace` 的套件在映像檔裡，
要改 Dockerfile 重新編映像。

```bash
# bcp-scripts：在你自己的機器上
git checkout -b fix/bump-cryptography

# 改 requirements.txt 裡那一行的版本
vim requirements.txt

git commit -am "fix: 升級 cryptography 修補 CVE-2026-XXXXX"
git push -u origin fix/bump-cryptography
# 開 MR → MR 的 sca-dtrack 會重掃 → 綠燈就可以合併
```

> ⚠️ **離線環境**：升版之前要先把新版 wheel 帶進 VM1 的
> `/run/media/root/D/python_env/req/`，否則正式機上裝不起來，
> 部署完才會爆。
>
> 合併後也要記得在 VM1 上實際更新 venv，並確認
> `python -m pip freeze` 與 `requirements.txt` 一致
> （不一致的話，下次掃的是「紙上的環境」）。

### 路線 B：在 D-Track 標記例外

**適用**：沒有修補版本，而且確認我們沒有用到觸發弱點的那個功能。

操作位置：**Project → Audit Vulnerabilities → 點該筆弱點 → 右側 Analysis**

| 狀態 | 什麼時候用 | 會解除擋門嗎 |
|---|---|---|
| `Not Affected` | 我們沒有用到觸發弱點的那個功能 | ✅ 會 |
| `False Positive` | SBOM 認錯套件或版本 | ✅ 會 |
| `Resolved` | 已經升級修掉了 | ✅ 會 |
| `Exploitable` | 確認會被打到 | ❌ 不會（本來就該紅） |
| `In Triage` | 還在評估 | ❌ **不會**——常見誤會 |

> 📸 **待補截圖**：Audit Vulnerabilities 頁面的 Analysis 下拉選單與 Details 欄位。

**四件一定要做的事：**

1. 選對狀態（`In Triage` 不會解除擋門）
2. **在 Details 欄寫清楚理由**——是誰、什麼時候、根據什麼判斷的
3. 勾 **Suppress**（讓它不再列入計數）
4. 到 MR 或 Redmine 留一筆紀錄

> ⚠️ **標記例外是一個「會讓紅燈變綠燈」的動作，應該跟改程式碼一樣被審視。**
> 「為什麼我們不受這個 CVE 影響」是稽核一定會問的問題，半年後沒有人記得。
> **規定：標記例外要在 MR 或 Redmine 上留紀錄，不是自己點一點就算。**

> 📌 **例外是綁在「專案 : 版本」上的。**
> SBOM 上傳時，專案版本用的是**分支名稱**（`bcp-scripts:main`、
> `bcp-scripts:fix/bump-xxx` 各自是一個 project version）。
> 在 `main` 上標的例外，**不保證**會自動套用到功能分支那個 version。
> 功能分支的 MR 還是紅的話，先確認你標的是不是同一個 version。

### 路線 C：排期處理（升級會壞，或確認有影響但一時修不掉）

1. 在 Redmine 開票，寫明 CVE、影響套件、預計處理時間
2. D-Track 上標 `Exploitable` 或留 `In Triage`，Details 寫上 Redmine 票號
3. **不要**為了讓紅燈消失而亂標 `Not Affected`

如果真的急著上線，見第 6 節「緊急放行」——但那是**有代價**的做法。

---

## 5. ③ 讓 D-Track 重算（★最常卡住的一步★）

擋門的判斷不是看你標了什麼，而是看 **D-Track 算出來的 metrics 數字**
（`/api/v1/metrics/project/{uuid}/current` 的 `critical` / `high`）。

**這個數字不是即時的。** 標記完例外之後 metrics 還是舊的，
直接重跑 job 會發現「明明標了還是紅的」。

**做法一（UI，建議）**：
專案頁面右上角 → **⋮ → Refresh Metrics**，等幾秒後重新整理，
確認 Critical / High 的數字真的降下來了。

> 📸 **待補截圖**：專案頁面的 Refresh Metrics 選單位置。

**做法二（API）**：

```bash
# 專案 UUID 就在 job log 的 D-Track 連結最後面
curl -s -X POST \
  -H "X-API-Key: <你的 API Key>" \
  "https://dtrack.dai.post.gov.tw/api/v1/metrics/project/<UUID>/refresh"

# 等幾秒，確認數字
curl -s -H "X-API-Key: <你的 API Key>" \
  "https://dtrack.dai.post.gov.tw/api/v1/metrics/project/<UUID>/current" \
  | python3 -m json.tool | grep -E '"critical"|"high"'
```

**看到 `critical: 0`（每季掃的話還要 `high: 0`）才往下走。**

---

## 6. ④ 重跑 job 確認

### MR 的紅燈（情況 A）

```
MR 頁面 → Pipeline → sca-dtrack job → 右上角 Retry
```

或直接推一個新 commit，pipeline 會整條重跑。

預期看到：

```
=======================================
🛡️  資安掃描結果（bcp-scripts:fix/bump-cryptography）
🔥 Critical : 0
🚨 High     : 2
⚠️  Medium   : 7
ℹ️  Low      : 12
=======================================
[ OK ]  SCA 檢查通過
```

綠燈之後，MR 還要滿足其他合併條件才按得下 Merge：

- Pipeline 全綠
- 至少 1 個**不是作者本人**的 approval
- 所有 discussion 都 resolved
- CODEOWNERS 指定的人審過（如果動到高風險檔案）

這些的設定與原理見
[GitLab維運手冊 · 04_帳號_權限_分支保護](../../GitLab維運手冊/日常維運/04_帳號_權限_分支保護.md#3-code-review-的強制性ee-版)。

### 每季弱掃的紅燈（情況 B）

排程 pipeline 不能直接「重跑排程」，改用**手動觸發**：

```
GitLab → Build → Pipelines → Run pipeline
  Branch: main
  Variables: SCHEDULE_TYPE = quarterly     ← ★不加這個，quarterly job 不會跑★
  → Run pipeline
  → 在 pipeline 頁面手動按下 sca-dtrack-quarterly（它是 manual job）
```

> `sca-dtrack-quarterly` 在 web 手動觸發時是 `when: manual`，
> 所以 pipeline 建立後還要再點一下那個 job 才會開始跑。

## 7. 緊急放行（最後手段）

> 🚨 **這一節的做法都會讓一個已知的資安風險進到正式機。**
> 只有在「營運中斷 vs 已評估過的風險」之間必須取捨時才用，
> 而且**一定要留紀錄、一定要排回頭修的時間**。

| 手段 | 做法 | 代價 |
|---|---|---|
| **改用手動觸發，關掉 High 擋門** | Run pipeline 時加 `DTRACK_FAIL_ON_HIGH = 0` | 只影響這一次，相對可控 |
| **暫時把 job 設成 allow_failure** | 改 `.gitlab-ci.yml`，job 加 `allow_failure: true` | 要走 MR，會被 CODEOWNERS 擋下來審——**這是刻意的** |
| **Maintainer 直接合併** | 需要有人有權限略過 pipeline 檢查 | 破壞「Pipelines must succeed」的保證，最不建議 |

**放行之後一定要做的三件事：**

1. Redmine 開票，寫明放行的 CVE、原因、預計修補時間
2. 在 MR 留言記錄是誰決定放行的
3. 排進下一次的處理清單，**不要讓它變成永久狀態**

> `.gitlab-ci.yml` 被 CODEOWNERS 列為 Maintainer 必審檔案，
> 就是為了讓「把資安檢查關掉」這件事**沒辦法悄悄發生**。
> 不要為了方便去拿掉那條 CODEOWNERS 規則。

## 8. 排查：紅燈但不是因為有弱點

不是每個紅燈都代表「掃到東西」。先看 job log 最後一段是哪一種：

| Log 訊息 | 意思 | 怎麼處理 |
|---|---|---|
| `[FAIL] 偵測到 N 個 Critical 弱點` | 真的掃到了 | 走第 2 節流程 |
| `偵測到 N 個 High 弱點，且 DTRACK_FAIL_ON_HIGH=1` | 每季掃掃到 High | 走第 2 節流程 |
| `等待 D-Track 分析逾時` | dtrack-server 太慢或掛了 | 見下方 |
| `上傳失敗，確認 ... 連得到、API Key 正確` | 連線或 API Key 問題 | 見下方 |
| `查不到專案 UUID` | 專案沒建成功（`autoCreate` 權限不足） | 檢查 API Key 有沒有 `PROJECT_CREATION_UPLOAD` |
| `產不出 SBOM：repo 裡沒有 requirements.txt，也沒有設定 DTRACK_IMAGE` | `dagster-workspace` 少設變數 | 補 `DTRACK_IMAGE` 這個 CI Variable |
| `無法解析 D-Track 回傳的弱點數` | API 回應異常 | 先確認 dtrack-server 正常，再重跑 |

**分析逾時**：

```bash
# 在 VM3
docker compose ps dtrack-server           # 是不是 healthy
docker logs --tail 100 dtrack-server      # 有沒有 exception
```

確認服務正常後重跑 job。如果是專案套件很多、分析本來就慢，
把 `DTRACK_POLL_MAX` 調大（預設 12 輪 × 5 秒 = 60 秒；每季掃已經是 36 輪 = 180 秒）。

> **不要**把逾時當成通過。`ci/build_sbom.sh` 刻意讓逾時 = 失敗：
> 「等不到結果就放行」等於把品質閘門變成裝飾品。

**上傳失敗 / API Key 問題**：

```bash
# 在 VM3 確認 D-Track 通得到
curl -sk https://dtrack.dai.post.gov.tw/api/version

# 確認 API Key 還有效（換掉 <KEY>）
curl -s -H "X-API-Key: <KEY>" \
  https://dtrack.dai.post.gov.tw/api/v1/project | head -c 200
```

回 401 就是 Key 被撤銷或打錯，重新產一把並更新 GitLab Variable `DTRACK_API_KEY`
（見 [進階調整 · 10](../進階調整/10_D-Track_專案_API_Key_與擋門門檻.md#2-api-key)）。

## 9. 每季弱掃的檢查清單

每季那一跑結束後，照這張表走一次：

```
[ ] 排程 pipeline 有跑起來（沒跑的話先確認排程還是 Activated）
[ ] 兩個 repo 的 sca-dtrack-quarterly 都跑了
[ ] job log 的四個數字有記錄下來（跟上一季比較）
[ ] Critical = 0；不是 0 的話已經開票或已修
[ ] High 逐一過一遍：升級 / 標例外 / 開票，三選一
[ ] 標成 Not Affected 的每一筆，Details 都有寫理由
[ ] 標記例外有在 Redmine 或 MR 留紀錄
[ ] bom.json artifact 有保留（稽核用，設定是保留 1 年）
[ ] 重跑到綠燈，或明確記錄「這一季剩下哪些未處理、為什麼」
```
