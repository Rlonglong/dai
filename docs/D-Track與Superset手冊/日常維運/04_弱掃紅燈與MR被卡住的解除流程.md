# 04 · 弱掃紅燈與 MR 被卡住的解除流程

> 這份文件在回答：**掃出弱點、pipeline 紅燈、MR 合併不了，現在該做什麼。**
> 從「先搞清楚是哪一種紅燈」開始，一步一步做到綠燈。
>
> 環境：Dependency-Track **v4.14.2**、GitLab **CE**。

---

## 1. 我們的擋門標準

| | 日常（MR / push / main） | 每季複掃（1/4/7/10 月 1 號 03:00） |
|---|---|---|
| job 名稱 | `sca-dtrack` | `sca-dtrack-quarterly` |
| **Critical** | 🚫 擋 | 🚫 擋 |
| **High** | 🚫 擋 | 🚫 擋 |
| **Medium** | ⚠️ 只警告 | 🚫 **擋** |
| Low | 記錄 | 記錄 |
| artifacts 保留 | 1 週 | **1 年**（稽核用） |

**兩個門檻都不含作業系統層套件**（`glibc`、`libc-bin`、`openssl`、`zlib`…）——
那些由 CI 自動放行，見第 2 節。

> **為什麼日常就擋到 High**：OS 層套件自動放行之後，剩下的 High 都是
> 「我們自己選的套件」，數量可控、也真的該處理。
> **每季多擋 Medium**：那一次專門用來清技術債，時間點固定、可以事先安排人力。

### 紅燈有兩種，影響範圍完全不同

| | A. MR 的 `sca-dtrack` 紅了 | B. 每季 `sca-dtrack-quarterly` 紅了 |
|---|---|---|
| 在哪裡看到 | 你自己開的 MR 頁面 | Build → Pipelines，`main` 上一條排程 pipeline |
| 直接後果 | **這個 MR 合併不了** | `main` 上出現紅燈紀錄 |
| 對其他人的影響 | 只影響你這個 MR | 不會擋住別人正在開的 MR |

> 📌 **每季掃出的 Medium 不會回頭去擋別人的 MR**（日常門檻只到 High）。
> 但它必須處理：`main` 留著紅燈紀錄稽核會問，而且今天的 Medium
> 下個月可能被重新評為 High——那時候就是真的全員卡住。

## 2. 作業系統層套件（libc 那一類）已經自動放行

容器映像檔的 SBOM 會把整個 base image 的 OS 套件也列進來：
`glibc`、`libc-bin`、`openssl`、`zlib`、`bash`、`coreutils`…

這些對我們來說**無法處理**：

1. 不是我們安裝的，是 base image 帶進來的
2. 不能單獨升級（要換整個 base image 版本）
3. 多數是 Debian/RHEL 已標記 will-not-fix，或不影響容器內的使用情境

如果不處理，每次掃描都會被幾百個 OS 弱點淹沒，
**真正該看的「我們自己裝的套件」反而看不到**——這才是最危險的狀態。

### 怎麼做的

CI 每次掃描時會自動跑 [`ci/dtrack_suppress_os.sh`](../../../ci/dtrack_suppress_os.sh)：

```
上傳 SBOM → 等分析完成 → 找出所有 OS 層元件的弱點
                            （purl 開頭是 pkg:deb/ pkg:rpm/ pkg:apk/）
                        → Analysis 標成 NOT_AFFECTED + Suppressed
                        → Details 寫入一段固定的系統放行說明
                        → 重算 metrics → 這些就不再列入 Critical/High/Medium
```

**範圍嚴格限定**：只處理 `pkg:deb/`、`pkg:rpm/`、`pkg:apk/` 這三種
（作業系統套件管理員安裝的東西）。
`pkg:pypi/`、`pkg:maven/`、`pkg:npm/` 這些「我們自己選的套件」**一律不碰**。

### Details 欄會留下什麼

在 D-Track 上點開任何一筆被自動放行的弱點，Details 欄會看到：

```
【系統自動放行 · 作業系統層套件】
放行日期：2026-08-07
放行來源：CI 自動化（bcp-scripts:main）
Pipeline：https://gitlab.dai.post.gov.tw/.../pipelines/1234

放行理由：
本元件屬於容器 base image 的作業系統套件（purl 為 pkg:deb / pkg:rpm / pkg:apk），
不是本專案自行安裝或選用的相依套件，無法單獨升級；
修補方式為改用已更新的 base image，屬於映像檔改版流程，
不在本專案的相依套件管理範圍內。

補償控制：
base image 版本由映像檔建置流程控管，隨映像檔改版一併更新。

規則出處：ci/dtrack_suppress_os.sh
※ 本筆為規則性自動放行，非個案人工評估。
  若此元件確實被本專案直接使用，請人工改回 Exploitable 並開票追蹤。
```

> ✅ 稽核問「這些為什麼沒處理」時，這段就是答案：
> 有明確規則、有時間、有 pipeline 連結可回溯，
> 也寫清楚了它是規則性放行而非個案評估。

### 要關掉或調整

| 想做什麼 | 怎麼做 |
|---|---|
| 整個關掉自動放行 | CI Variable 設 `DTRACK_OS_SUPPRESS = 0` |
| 先看會放行哪些、不真的送出 | 設 `DTRACK_SUPPRESS_DRY_RUN = 1` 跑一次 |
| 某個 OS 套件我們其實有直接用到 | 到 D-Track 人工改回 `Exploitable`、取消 Suppress，並開票追蹤 |

> ⚠️ 這支腳本需要 API Key 有 **`VULNERABILITY_ANALYSIS`** 權限——
> 那是一個「能讓紅燈變綠燈」的權限。
> 因為腳本的範圍寫死在程式碼裡（只碰三種 OS purl）、而且程式碼要走 MR 才能改，
> 所以這個授權是可控的。細節見
> [附錄 A · 第 3 節](../附錄/A_D-Track_Analysis狀態與權限對照.md#3-team-權限對照)。

## 3. 通用解除流程（四步）

```
① 看懂是什麼    → job log 的連結點進 D-Track，確認套件、CVE、嚴重度
② 決定怎麼處理  → 升級版本 ／ 標記例外 ／ 排期處理
③ 標記／升級    → 在 D-Track 上做，或改 requirements.txt
④ 重跑 job     → Retry，看到 [ OK ] 才算解除
```

> 💡 **metrics 重算不用你手動點。**
> `ci/build_sbom.sh` 每次執行都會自己呼叫 Refresh Metrics 再讀數字，
> 所以你在網頁上標記完，直接回 GitLab 按 Retry 就好。

## 4. ① 看懂是什麼

Job log 長這樣：

```
=======================================
🛡️  資安掃描結果（bcp-scripts:main）
🔥 Critical : 0
🚨 High     : 3
⚠️  Medium   : 7
ℹ️  Low      : 12
   D-Track  : https://dtrack.dai.post.gov.tw/projects/a3f2b91c-...
=======================================
[FAIL]  偵測到 3 個 High 弱點（門檻：High 以上擋）→ 阻擋 Pipeline

  怎麼讓它過（三條路，擇一）：
    1. 升級套件版本  ← 正解。...
    2. 標記為不受影響  ← ...
    3. 排期處理  ← ...
```

點那個 D-Track 連結，進到該專案的 **Audit Vulnerabilities** 分頁：

![D-Track 專案的 Audit Vulnerabilities 分頁](./images/05_dtrack_audit_vulnerabilities.png)

要看的欄位：

| 欄位 | 你要從它得到什麼 |
|---|---|
| **Component** | 是哪個套件、目前用哪一版 |
| **Group** | 套件的命名空間（例如 `com.fasterxml.jackson.core`） |
| **Vulnerability** | CVE 編號，點進去有完整說明 |
| **Severity** | Critical / High / Medium / Low |
| **Analyzer** | 是哪個掃描器報的（`Trivy` 代表來自容器映像掃描） |
| **Analysis** | 目前的處理狀態，`-` 代表還沒有人看過 |
| **Suppressed** | 有沒有被放行（OS 層套件會在這裡打勾） |

> 💡 想看被自動放行的 OS 套件，把上方的 **Show suppressed findings** 打開。

點 CVE 編號會進到弱點詳情頁，**Fixed in 是最重要的資訊**——決定你走哪條路：

![CVE 詳情頁](./images/06_dtrack_vulnerability_detail.png)

## 5. ② 決定怎麼處理

```
                有沒有修補版本？
                 │           │
                有           沒有
                 │           │
        升級會不會壞？        我們有沒有用到那個弱點功能？
         │        │            │            │
        不會      會           沒用到        有用到
         │        │            │            │
      ★路線A★  ★路線C★     ★路線B★      ★路線C★
      直接升級  排期處理     標記例外      排期處理／緊急放行
```

### 路線 A：升級套件版本（**正解，優先走這條**）

只有 `bcp-scripts` 走 `requirements.txt`；`dagster-workspace` 的套件在映像檔裡，
要改 Dockerfile 重新編映像。

```bash
# bcp-scripts：在你自己的機器上
git checkout -b fix/bump-cryptography

# 改 requirements.txt 裡那一行的版本
vim requirements.txt

git commit -am "fix: 升級 cryptography 修補 CVE-2026-XXXXX"
git push -u origin fix/bump-cryptography
# 開 MR → MR 的 sca-dtrack 會重掃 → 綠燈就可以合併
```

> ⚠️ **離線環境**：升版之前要先把新版 wheel 帶進 VM1 的
> `/run/media/root/D/python_env/req/`，否則正式機上裝不起來，部署完才會爆。
>
> 合併後也要在 VM1 上實際更新 venv，並確認
> `python -m pip freeze` 與 `requirements.txt` 一致
> （不一致的話，下次掃的是「紙上的環境」）。

### 路線 B：在 D-Track 標記為不受影響（★這條路要寫清楚理由★）

**適用**：沒有修補版本，或確認我們沒有用到觸發弱點的那個功能。

**完整操作路徑（D-Track v4.14.2）**：

```
1. 左側選單 Projects → 點該專案名稱
   （版本要對！版本 = 分支名稱，見第 7 節）
2. 上方分頁選 Audit Vulnerabilities
3. 找到那一筆，點最左邊的 ▶（展開箭頭）
4. 展開後出現 Analysis 區塊：
     Analysis       → 選 Not Affected
     Justification  → 選最貼近的一項
     Details        → ★寫理由，見下方範本★
     Suppress       → 打勾
5. 按 Update
6. 回 GitLab，該 job 按 Retry
```

**Analysis 狀態怎麼選**：

| 狀態 | 什麼時候用 | 會解除擋門嗎 |
|---|---|---|
| `Not Affected` | 我們沒有用到觸發弱點的那個功能 | ✅ 會 |
| `False Positive` | SBOM 認錯套件或版本 | ✅ 會 |
| `Resolved` | 已經升級修掉了 | ✅ 會 |
| `Exploitable` | 確認會被打到 | ❌ 不會（本來就該紅） |
| `In Triage` | 還在評估 | ❌ **不會**——最常見的誤會 |

**Details 欄的寫法（人工評估用，請照這個格式）**：

```
【人工評估放行】
評估日期：2026-08-07
評估人：王小明
CVE：CVE-2026-54515（jackson-databind 2.21.4，Medium）

評估結論：Not Affected

理由：
本專案僅使用 jackson-databind 的 ObjectMapper 讀取固定結構的內部設定檔，
未使用 CVE 影響的 @JsonIgnoreProperties + @JsonFormat 大小寫不敏感組合，
也不會反序列化外部來源的 JSON。

補償控制：
輸入來源限於本機設定檔，不接受外部輸入。

追蹤：Redmine #1234（下次 base image 改版時一併升級）
```

四個要素缺一不可：**誰、什麼時候、根據什麼判斷、有沒有補償控制**。

> ⚠️ **標記例外是一個「會讓紅燈變綠燈」的動作，應該跟改程式碼一樣被審視。**
> 「為什麼我們不受這個 CVE 影響」是稽核一定會問的問題，半年後沒有人記得。
> **規定：人工標記例外要在 MR 或 Redmine 上留紀錄，不是自己點一點就算。**

### 路線 C：排期處理（升級會壞，或確認有影響但一時修不掉）

1. 在 Redmine 開票，寫明 CVE、影響套件、預計處理時間
2. D-Track 上標 `Exploitable`，Details 寫上 Redmine 票號
3. **不要**為了讓紅燈消失而亂標 `Not Affected`

急著上線的話見第 8 節「緊急放行」——那是**有代價**的做法。

## 6. ④ 重跑 job

### MR 的紅燈（情況 A）

```
MR 頁面 → 下方 Pipeline 區塊 → 點 pipeline 編號
  → 找到 sca-dtrack job → 進 job 頁面 → 右上角 Retry（⟳ 圖示）
```

或直接推一個新 commit，pipeline 會整條重跑。

預期看到：

```
=======================================
🛡️  資安掃描結果（bcp-scripts:fix/bump-cryptography）
🔥 Critical : 0
🚨 High     : 0
⚠️  Medium   : 7
ℹ️  Low      : 12
=======================================
[WARN]  有 7 個 Medium 弱點，這一關不擋，每季複掃時會擋
[ OK ]  SCA 檢查通過
```

綠燈之後，MR 還要滿足其他合併條件才按得下 Merge：

- Pipeline 全綠（`Pipelines must succeed`）
- 所有 discussion 都 resolved（`All threads must be resolved`）
- **由 Maintainer 按下 Merge**——我們用的是 GitLab CE，沒有核准人數的功能，
  改成把 Merge 權限收在 Maintainer 手上，作者自己合不了

設定與原理見
[GitLab維運手冊 · 04_帳號_權限_分支保護](../../GitLab維運手冊/日常維運/04_帳號_權限_分支保護.md#3-code-review-的強制性ce-版)。

### 每季弱掃的紅燈（情況 B）

排程 pipeline 不能直接「重跑排程」，改用**手動觸發**：

```
該 project → Build → Pipelines → 右上角 Run pipeline
  Run for branch name : main
  Variables           : Key = SCHEDULE_TYPE   Value = quarterly
                        ← ★不加這個，quarterly job 不會出現★
  → Run pipeline
  → pipeline 頁面上找到 sca-dtrack-quarterly，點它的 ▶ 才會開始跑
```

> `sca-dtrack-quarterly` 在 web 手動觸發時是 `when: manual`，
> 所以 pipeline 建立後還要再點一下那個 job。

## 7. 「下次 MR 會不會自動確認我改好了？」——會

**每一次 pipeline 執行都是重新量測，不是讀舊紀錄。** 流程是：

```
每次 sca-dtrack 執行
  1. 重新產生 SBOM（讀當下的 requirements.txt／映像檔）
  2. 重新上傳到 D-Track
  3. D-Track 用「當下最新的弱點資料庫」重新分析
  4. 自動放行 OS 層套件
  5. 呼叫 Refresh Metrics，重新計算數字
  6. 讀 metrics 判斷擋不擋
```

所以：

| 你做了什麼 | 下次 pipeline 會不會反映 |
|---|---|
| 升級了套件版本 | ✅ 會，SBOM 重產就看得到新版本 |
| 在 D-Track 標了 Not Affected + Suppress | ✅ 會，metrics 重算後就不列入計數 |
| 只是標 `In Triage` | ❌ 不會，那個狀態不解除擋門 |
| 標在**別的分支版本**上 | ❌ 不會，見下方 |

> ⚠️ **例外是綁在「專案 : 版本」上的，版本 = 分支名稱。**
> `bcp-scripts:main` 和 `bcp-scripts:fix/bump-xxx` 在 D-Track 是**兩個不同的
> project version**，各自有各自的 Analysis 紀錄。
>
> 所以：在 `main` 上標的例外，**不保證**自動套用到你的功能分支。
> MR 還是紅的話，先看 job log 印的是哪一個 `專案名:版本`，
> 到**那一個** version 上再標一次。
>
> OS 層套件不受這個影響——CI 每次跑都會對「當下這個 version」重新放行一遍。

**合併進 `main` 之後**：`main` 上會再跑一次 `sca-dtrack`，
同樣是重新量測，所以你在功能分支標的例外要在 `main` 上再標一次。
（這也是為什麼 OS 層套件要做成自動化——人工標記完全跟不上分支的數量。）

## 8. 緊急放行（最後手段）

> 🚨 **這一節的做法都會讓一個已知的資安風險進到正式機。**
> 只有在「營運中斷 vs 已評估過的風險」之間必須取捨時才用，
> 而且**一定要留紀錄、一定要排回頭修的時間**。

| 手段 | 做法 | 代價 |
|---|---|---|
| **手動觸發時放寬門檻** | Run pipeline 時加 `DTRACK_FAIL_ON_HIGH = 0`（每季掃再加 `DTRACK_FAIL_ON_MEDIUM = 0`） | 只影響這一次，相對可控 |
| **暫時把 job 設成 allow_failure** | 改 `.gitlab-ci.yml`，job 加 `allow_failure: true` | 要走 MR，且 `.gitlab-ci.yml` 是 Maintainer 才合得了的檔案——**這是刻意的** |
| **請 Maintainer 略過檢查合併** | 需要有人願意承擔 | 破壞「Pipelines must succeed」的保證，最不建議 |

**放行之後一定要做的三件事：**

1. Redmine 開票，寫明放行的 CVE、原因、預計修補時間
2. 在 MR 留言記錄是誰決定放行的
3. 排進下一次的處理清單，**不要讓它變成永久狀態**

## 9. 排查：紅燈但不是因為有弱點

不是每個紅燈都代表「掃到東西」。先看 job log 最後一段是哪一種：

| Log 訊息 | 意思 | 怎麼處理 |
|---|---|---|
| `偵測到 N 個 Critical 弱點` | 真的掃到了 | 走第 3 節流程 |
| `偵測到 N 個 High 弱點（門檻：High 以上擋）` | 日常門檻擋下 | 走第 3 節流程 |
| `偵測到 N 個 Medium 弱點（門檻：Medium 以上擋）` | 每季門檻擋下 | 走第 3 節流程 |
| `D-Track 回 401/403：API Key 缺少 VULNERABILITY_ANALYSIS 權限` | 自動放行做不到 | 補權限，見[附錄 A](../附錄/A_D-Track_Analysis狀態與權限對照.md#3-team-權限對照) |
| `等待 D-Track 分析逾時` | dtrack-server 太慢或掛了 | 見下方 |
| `上傳失敗，確認 ... 連得到、API Key 正確` | 連線或 API Key 問題 | 見下方 |
| `查不到專案 UUID` | 專案沒建成功（`autoCreate` 權限不足） | 檢查 API Key 有沒有 `PROJECT_CREATION_UPLOAD` |
| `產不出 SBOM：repo 裡沒有 requirements.txt，也沒有設定 DTRACK_IMAGE` | `dagster-workspace` 少設變數 | 補 `DTRACK_IMAGE` 這個 CI Variable |
| `無法解析 D-Track 回傳的弱點數` | API 回應異常 | 先確認 dtrack-server 正常，再重跑 |

**分析逾時**：

```bash
# 在 VM3
cd /run/media/root/D/deploy
docker compose ps dtrack-server           # 是不是 healthy
docker logs --tail 100 dtrack-server      # 有沒有 exception
```

確認服務正常後重跑 job。如果是專案套件很多、分析本來就慢，
把 `DTRACK_POLL_MAX` 調大（預設 12 輪 × 5 秒 = 60 秒；每季掃已經是 36 輪 = 180 秒）。

> **不要**把逾時當成通過。`ci/build_sbom.sh` 刻意讓逾時 = 失敗：
> 「等不到結果就放行」等於把品質閘門變成裝飾品。

**上傳失敗 / API Key 問題**：

```bash
# 在 VM3 確認 D-Track 通得到
curl -sk https://dtrack.dai.post.gov.tw/api/version

# 確認 API Key 還有效（換掉 <KEY>）
curl -s -H "X-API-Key: <KEY>" \
  https://dtrack.dai.post.gov.tw/api/v1/project | head -c 200
```

回 401 就是 Key 被撤銷或打錯，重新產一把並更新 GitLab 的
**Project variables** `DTRACK_API_KEY`
（見 [進階調整 · 10](../進階調整/10_D-Track_專案_API_Key_與擋門門檻.md#2-api-key)）。

## 10. 每季弱掃的檢查清單

```
[ ] 排程 pipeline 有跑起來（沒跑先確認排程還是 Activated）
[ ] 兩個 repo 的 sca-dtrack-quarterly 都跑了
[ ] job log 的四個數字有記錄下來（跟上一季比較）
[ ] Critical = 0、High = 0
[ ] Medium 逐一過一遍：升級 / 標例外 / 開票，三選一
[ ] 人工標成 Not Affected 的每一筆，Details 都有寫四要素
[ ] 抽查幾筆自動放行的 OS 套件，確認 Details 有寫入系統放行說明
[ ] 標記例外有在 Redmine 或 MR 留紀錄
[ ] bom.json artifact 有保留（稽核用，設定是保留 1 年）
[ ] 重跑到綠燈，或明確記錄「這一季剩下哪些未處理、為什麼」
```
