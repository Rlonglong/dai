## 資料夾結構

> ⚠️ **路徑對照**：本資料夾 `dagster_workspace/` 就是容器裡的 `/app/workspace/`
> （docker 掛載的路徑，**非實際路徑**），對應 VM4 主機上的
> `/data/deploy/workspace/dagster_workspace/`（**實際掛載路徑**）。
> 程式碼裡看到 `/app/workspace/xxx`，就是這裡的 `xxx`。

```
dagster_workspace/                ← ★整個資料夾 = CD 的部署單位★
│
├── workspace.yml                 ← Dagster 要載入哪個 Python 模組
├── dagster_home/
│   └── dagster.yaml              ← Dagster 實例設定（併發、log、自動觸發）
│   └── （storage/ history/ logs/ 等執行期產物不進版控，見下方 .gitignore 說明）
│
├── dagster_code/                 ← Dagster 的 Python 程式
│   ├── __init__.py               ← <常態不需要改> 總入口：註冊 asset / job / sensor / resource
│   ├── assets.py                 ← <常態不需要改> 核心：EL 節點工廠、dbt 資產、匯出資產
│   ├── table_mapping.py          ← ★最常改的檔案★ 來源表(TABLE_CSV_MAPPING)、匯出(SQL_TO_CSV_MAPPING)
│   ├── sensors.py                ← <常態不需要改> 檔案到站偵測、失敗告警
│   ├── selections.py             ← <常態不需要改> 動態組出「月檔」「手動專用」的資產集合
│   ├── pipes_ssh_client.py       ← <常態不需要改> SSH 到 VM1 執行腳本的連線元件
│   ├── log_utils.py              ← <常態不需要改> log 分流（UI 只放狀態、明細走 rsyslog）
│   ├── .env                      ← ★不進版控、也不會被 rsync 覆蓋★ 資料庫連線帳密
│   └── db_sync/                  ← DB 直連同步線（跟檔案線平行的另一套）
│       ├── config.py             ← 設定檔：DB_SYNC_MAPPING
│       ├── assets.py             ← 撈取 / 加密 / 入庫 / 清理 四個節點
│       └── sensors.py            ← 輪詢來源 DB 筆數是否穩定
│
└── dbt_project/                  ← dbt 專案（SQL 轉換邏輯）
    ├── dbt_project.yml           ← dbt 專案設定
    ├── profiles.yml              ← ★不進版控、也不會被 rsync 覆蓋★ 資料庫連線
    ├── profiles.yml.example      ← 上面那份的範本，新環境複製一份改名即可
    ├── models/
    │   ├── sources.yml           ← ★所有 dbt 要用的來源表都要在這裡登記★
    │   ├── _groups.yml           ← 群組與負責人
    │   ├── intermediate/         ← 中介層（去沖正、淨額表）
    │   └── *.sql                 ← 產出層：37 支詐欺偵測模型
    ├── snapshots/                ← 2 支緩慢變動維度快照
    ├── macros/                   ← 共用的 Jinja macro
    │   ├── anti_fraud/           ← get_config() 代碼註冊表、出入帳判斷式
    │   └── global/               ← safe_divide 等通用工具
    ├── target/                   ← ★編譯產出★ 不進版控，由 CD 在部署後重新產生
    ├── logs/                     ← dbt 自己的執行 log，不進版控
    └── dbt_packages/             ← dbt 套件（目前無）
```

### 版控範圍與部署範圍不是同一件事

| 檔案 | 進 Git？ | 會被 rsync 推到 VM4？ | VM4 上誰產生它 |
|---|---|---|---|
| `dagster_code/*.py`、`dbt_project/models/*.sql` | ✅ | ✅ | GitLab CD |
| `dagster_code/.env`、`dbt_project/profiles.yml` | ❌ | ❌（在 rsync 排除清單，`--delete` 不會刪它） | 部署時人工建立 |
| `dbt_project/target/`（含 `manifest.json`） | ❌ | ❌ | CD 部署後執行 `dbt parse` 重產 |
| `dbt_project/logs/`、`dagster_home/storage/` | ❌ | ❌ | 執行期自己產生 |
| `docs/`、`ci/`、`.gitlab-ci.yml` | ✅ | ❌（不是執行期需要的東西） | — |

兩份清單管兩件不同的事，**都要維護**：

- [`.gitignore`](../../.gitignore) — 決定**什麼進版控**（repo 根目錄相對路徑）
- [`deploy_exclude.txt`](../../deploy_exclude.txt) — 決定 **rsync 不傳、也不刪**什麼
  （`dagster_workspace/` 相對路徑）

新增一種「執行期才產生、不該被 `--delete` 洗掉」的檔案時，**兩份都要加**。
細節見 [GitLab維運手冊 · 11_CD_rsync部署機制](../GitLab維運手冊/進階調整/11_CD_rsync部署機制.md)。

## 不在這個資料夾、但流程強相依的東西

| 東西 | 位置 | 說明 |
|---|---|---|
| VM1 執行腳本 | VM1 `/home/bcp_runner/scripts/` | 真正做事的地方：下載、加解密、清洗、BCP、匯出。**另一個 GitLab repo**，見 [GitLab維運手冊](../GitLab維運手冊/README.md) |
| VM1 清洗函式 | VM1 `/home/bcp_runner/scripts/clean_functions/` | 每張表一支 `{表名}_CLEAN.py` |
| VM1 機密 | VM1 `/home/bcp_runner/.env` | ZIP 密碼、來源 DB 解密金鑰 |
| VM4 機密 | `dagster_code/.env` | 我方 DB 連線帳密 |
| dbt 編譯產出 | `dbt_project/target/` | 部署後由 CD 重新產生，不進版控 |

## 修改後要做什麼

> 程式碼由 **GitLab CI/CD** 同步到 VM4：合併進 `main` → CD 用 rsync 推到 VM4 →
> 重新產生 dbt manifest。所以正常流程是
> **開分支 → push（本地 hook 先擋一次）→ 開 MR → code review → 合併 main → 等 pipeline 綠燈 → 到 UI 做 Reload**。
>
> 完整流程見 [GitLab維運手冊 · 01_開發人員_日常開發流程](../GitLab維運手冊/日常維運/01_開發人員_日常開發流程.md)。

| 改了什麼 | 合併 main 後等 CD | Reload definitions | 重啟容器 |
|---|---|---|---|
| `table_mapping.py`、`db_sync/config.py` | ✓ | ✓ | ✗ |
| `assets.py`、`sensors.py`、`selections.py` | ✓ | ✓ | ✗ |
| dbt model、snapshot、`sources.yml`、`macros/` | ✓（順便重產 manifest） | ✓ | ✗ |
| `dagster.yaml`、`workspace.yml` | ✓ | ✗ | **✓** |
| VM1 上的腳本 | 走**另一個 repo** 的 pipeline，推到 VM1 | ✗ | ✗（下次執行就生效） |

詳細步驟見 [02_開發人員_UI操作手冊.md](./日常維運/02_開發人員_UI操作手冊.md)。
