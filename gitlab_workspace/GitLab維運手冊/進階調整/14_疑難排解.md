# 14 · 疑難排解

症狀 → 原因 → 解法。找不到的話往下看第 6 節的通用診斷步驟。

---

## 1. 本地 hook

| 症狀 | 原因 | 解法 |
|---|---|---|
| `git commit` 完全沒跑檢查 | hook 沒裝 | `ci/install_hooks.sh` |
| `找不到 gitleaks 執行檔` | 不在 PATH | `export GITLEAKS_BIN=/path/to/gitleaks` 並寫進 `~/.bashrc` |
| 所有工具都顯示 `⚠️ 找不到` | venv 沒啟動 | `source ~/.venv/bin/activate`，或設 `DAI_VENV` 環境變數 |
| hook 在 Windows 上沒作用 | 換行符 / 執行權限 | 用 Git Bash 或 WSL；`chmod +x ci/hooks/*` |
| push 第一次很慢 | 新分支要掃整批 commit | 正常，之後只掃增量 |
| `._foo.py` 被掃出一堆錯 | macOS AppleDouble 檔 | hook 已自動過濾；已經 `git add` 進去的話 `git rm --cached '._*'` |
| 改了 hook 但沒生效 | `core.hooksPath` 沒設對 | `git config --get core.hooksPath` 應該是 `ci/hooks` |

## 2. 伺服器端 pre-receive

| 症狀 | 原因 | 解法 |
|---|---|---|
| `! [remote rejected] (pre-receive hook declined)` 但沒有錯誤訊息 | hook 腳本本身出錯（不是偵測到金鑰） | VM3 上 `docker exec gitlab tail -100 /var/log/gitlab/gitaly/current` |
| `[DAI] 伺服器端找不到 gitleaks` | GitLab 容器重建，`/usr/local/bin/gitleaks` 沒了 | 重新 `docker cp`；長期解法見 [10_CI_Pipeline設定詳解 · 3-5](./10_CI_Pipeline設定詳解.md#3-5-讓它在容器重建後還在) |
| hook 完全沒被觸發 | 放錯目錄，或沒有執行權限 | 確認在 `/var/opt/gitlab/gitaly/custom_hooks/pre-receive.d/`、`chmod 755`、`chown git:git` |
| 推大分支時 hook 跑很久 | 第一次推新分支會掃 `--not --all` 範圍 | 正常。真的太久的話先 push 一個小的基底分支 |
| 本地過了但伺服器擋 | 兩邊 `.gitleaks.toml` 版本不同 | hook 會優先讀「這次推上來的」那份，所以把 allowlist 修改跟程式碼放同一個 commit |

> 💡 **hook 沒裝好時是「擋下所有 push」而不是「放行」**——這是刻意的。
> 靜默失效的資安控制比沒有控制更危險。

## 2.5 導入第一天：`secret-scanning` 的 history 掃描就紅了

**這很常見，而且通常是真的。**

`ci/check_secrets.sh history` 掃的是**整條 git 歷史**，不是只有現在的檔案。
所以只要曾經有人 commit 過金鑰，就算後來刪掉了，這一關還是會紅。

> 📌 **本 repo 目前就有一筆**：`README.md` 在早期的 commit 裡有一組
> Keycloak 的 Superset client secret（現在的版本已經換成佔位符）。
> 導入 CI 時這一關會紅，處理方式見下面。

### 處理順序（不能跳過第 1 步）

```
1. 換掉金鑰       ← ★最重要★ 進過 git 就當作已外洩，清歷史不能代替換金鑰
2. 現在的檔案改掉  ← 換成佔位符或改讀環境變數
3. 清歷史         ← 讓 history 掃描變綠
4. 重新 clone     ← 通知所有人
```

**第 1 步（以本 repo 那筆為例）：**

```bash
# 在 Keycloak（VM5）產生新的 client secret
# Clients → superset → Credentials → Regenerate
# 然後同步更新 VM5 的 superset 設定並重啟
```

**第 3 步，清歷史：**

```bash
# git filter-repo 不是 git 內建的，要另外裝
pip install git-filter-repo

# 只改那一個字串，不刪整個檔案（README.md 還要留著）
cat > /tmp/replace.txt <<'EOF'
PQGOjCiQ9lNIy46PRoqgsjEU1b2MVcYD==>YourSupersetOidcSecret
EOF
git filter-repo --replace-text /tmp/replace.txt --force

# 確認乾淨了
ci/check_secrets.sh history

# 強制推送（main 是保護分支，要暫時解除保護或請 Owner 執行）
git push --force-with-lease origin main
```

**第 4 步：** 通知所有人刪掉本地 clone 重新 clone。
`filter-repo` 會改寫所有 commit hash，沒重新 clone 的人下次 push 會製造出重複歷史。

### 如果暫時還不能清歷史

清歷史需要協調所有人重新 clone，不一定能馬上做。過渡期的作法：

```toml
# .gitleaks.toml
[allowlist]
commits = [
    # README.md 早期版本裡的 Superset OIDC client secret。
    # 金鑰已於 2026-__-__ 在 Keycloak 上輪替作廢，此處僅為讓 history 掃描通過。
    # ★ 預計於 ____ 執行 git filter-repo 清除後，刪掉這一行 ★
    "37a7fff9",
]
```

> ⚠️ **這是暫時措施，不是解法。**
> 加了之後一定要在 issue / Redmine 上開一張票追蹤，
> 不然它會永遠留在設定檔裡，而且以後沒有人記得為什麼。
> **前提是第 1 步（換金鑰）已經做完了** —— 沒換金鑰就 allowlist，
> 等於把外洩的金鑰標記成「可以忽略」。

## 3. CI pipeline

| 症狀 | 原因 | 解法 |
|---|---|---|
| pipeline 一直 pending | runner 離線或 tag 對不上 | Admin Area → Runners 看狀態；確認 job 的 `tags:` 有對應的 runner |
| `這次沒有檔案變動，品質檢查略過` 但明明有改 | shallow clone 算不出比較基準 | 確認 `GIT_DEPTH: 0` 有設 |
| `format-check` 紅在你沒改的地方 | 該檔案是舊格式，動到就要整檔重排 | `black <檔案>`；或先做一次全庫格式化（`ci/format_all.sh`） |
| `dbt-parse` 紅 | `ref()` 指到不存在的模型、`sources.yml` 沒登記 | 訊息很直白，照著修 |
| `sca-dtrack` 說「產不出 SBOM」 | 沒有 `requirements.txt` 也沒設 `DTRACK_IMAGE` | 設 `DTRACK_IMAGE` 變數 |
| `sca-dtrack` 等待逾時 | dtrack-server 慢或掛了 | `docker logs dtrack-server`；或調高 `DTRACK_POLL_MAX` |
| 同一個 commit 跑兩條 pipeline | rules 少了 `$CI_OPEN_MERGE_REQUESTS == null` | 見 [10_CI_Pipeline設定詳解 · 第 5 節](./10_CI_Pipeline設定詳解.md#5-rules-為什麼寫成那樣) |
| runner 上缺工具 | 容器重建後套件沒了 | `docker exec -it gitlab-runner-ci bash` 重裝；長期做進自訂 image |

## 4. CD 部署

| 症狀 | 原因 | 解法 |
|---|---|---|
| `缺少必要的 CI/CD Variable` | 變數勾了 Protected，但分支不是保護分支 | 確認 `main` 有設成 Protected branch |
| `SSH 連線失敗，或目標目錄不存在` | 見下方細分 | ↓ |
| └ `Permission denied (publickey)` | 公鑰沒放進目標機的 `authorized_keys` | 見 [附錄 A](../附錄/A_gitlab_runner帳號與SSH金鑰.md) |
| └ `Host key verification failed` | `DEPLOY_KNOWN_HOSTS` 內容不對或目標機換過 host key | 重新取得 host key |
| └ `Connection timed out` | 防火牆沒開 VM3 → 目標機 22 port | 通知網管 |
| └ `test -d 失敗` | 目標目錄不存在，或 `gitlab_runner` 沒有讀取權限 | `mkdir -p` + `setfacl` |
| `UNPROTECTED PRIVATE KEY FILE` | File 變數落地的權限是 644 | `deploy_rsync.sh` 已用 `install -m 600` 處理；不要改掉那行 |
| rsync `No space left on device` | 目標機磁碟滿 | `df -h`；清 `dbt_project/logs/`、舊的 `target/` |
| rsync 每次都全量重傳 | 少了 `--checksum` | CI 每次全新 checkout，mtime 一定不同 |
| **`.env` 在部署後消失** | ★排除清單漏了★ | 立刻從備份還原；補進 `deploy_exclude.txt`。見 [11 · 第 3 節](./11_CD_rsync部署機制.md#3-排除清單--刪除保護清單最重要的一節) |
| post-deploy `sudo: a password is required` | sudoers 沒設或設錯 | `visudo -c` 驗證 `/etc/sudoers.d/dai-gitlab-runner` |
| post-deploy `dbt parse` 失敗 | 模型語法錯 / `ref()` 指錯 | 看 job log 的 dbt 訊息。**檔案已經推上去了但 manifest 沒更新**，要盡快處理 |
| post-deploy 說「`.env` 不存在」 | 正式機上根本沒建過 | 依部署手冊建立 |
| 部署卡住不動 | 另一個 deploy job 佔著 `resource_group` | 等前一個跑完，或去 Pipelines 取消它 |

## 5. 雜湊對帳

| 症狀 | 原因 | 解法 |
|---|---|---|
| `兩邊都有但內容不同` | **有人直接改了正式機** | 見 [12 · 第 4 節](./12_同步完整性稽核.md#4-對不上的時候怎麼查)。**先保留證據再處理** |
| `只有 GitLab 有` | 同步沒完成 | 重跑 deploy job（安全） |
| `只有正式機有` | 備份檔／臨時檔，或排除清單漏了 | 確認後重跑 deploy；是執行期產物的話補進兩份清單 |
| `目標端雜湊計算失敗` | `gitlab_runner` 對目標目錄沒有讀取權限 | `setfacl -R -m u:gitlab_runner:rX <目錄>` |
| 每天都紅、差異都是同一批檔案 | 排除清單少了某個執行期產物 | 把它加進 `deploy_exclude.txt` **和** `.gitignore` |
| 剛部署完就紅 | rsync 傳了但 post-deploy 改了檔案內容 | 檢查 post-deploy 有沒有動到檔案內容（chmod/chown 不影響雜湊，但重寫檔案會） |

## 6. 通用診斷步驟

卡住又對不上上面任何一條時，照這個順序查：

```bash
# 1. runner 活著嗎
#    GitLab UI → Admin Area → CI/CD → Runners

# 2. runner 上的環境對嗎
docker exec -it gitlab-runner-cd bash
whoami                  # 應該是 gitlab_runner
which rsync ssh         # 兩個都要有
ls -la ~/.ssh/          # 私鑰 600、known_hosts 644

# 3. 手動走一次 SSH
ssh -i ~/.ssh/gitlab_to_vm4 \
    -o UserKnownHostsFile=~/.ssh/known_hosts \
    -o StrictHostKeyChecking=yes \
    gitlab_runner@<VM4_IP> 'echo OK; id; ls -la <DEPLOY_PATH>'

# 4. 手動走一次 dry-run
export DEPLOY_HOST=... DEPLOY_USER=gitlab_runner DEPLOY_PATH=... \
       DEPLOY_SSH_KEY=~/.ssh/gitlab_to_vm4 \
       DEPLOY_KNOWN_HOSTS=~/.ssh/known_hosts \
       SOURCE_DIR=dagster_workspace
ci/deploy_rsync.sh --dry-run

# 5. 手動對一次雜湊
ci/verify_sync.sh

# 6. 看 rsyslog 有沒有留下線索（VM4）
sudo grep 'dai/gitlab-sync' /data/log/dai/vm3-*/*.log | tail -30
```

## 7. 什麼時候該找誰

| 情況 | 找誰 | 急迫性 |
|---|---|---|
| 雜湊對帳出現「內容不同」且查不出是誰改的 | 資安 + 系統負責人 | **立即** |
| `.env` 在部署後消失 | 系統負責人 | **立即**（服務已中斷） |
| GitLab 服務掛掉 | 系統負責人 | 立即 |
| deploy 紅燈超過兩小時沒人處理 | 系統負責人 | 立即 |
| pre-receive hook 失效（推得上含金鑰的東西） | 資安 + GitLab 管理員 | 立即 |
| runner 重啟後還是離線 | 系統負責人 | 當天 |
| CI 某個 job 一直誤判 | 該 job 的維護者 | 當週 |
