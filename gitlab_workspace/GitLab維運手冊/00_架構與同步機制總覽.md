# 00 · 架構與同步機制總覽

第一次接觸這套 CI/CD 的人請先看完這篇。

---

## 1. 兩個 repo，各推各的

| repo | 內容 | 部署到 | 部署路徑 |
|---|---|---|---|
| `dagster-workspace` | Dagster 程式 + dbt 專案 + 文件 | **VM4** | `/data/deploy/workspace/dagster_workspace/` |
| `bcp-scripts` | VM1 的執行腳本與清洗函式 | **VM1** | `/home/bcp_runner/scripts/` |

**為什麼拆兩個而不是一個？**

| 理由 | 說明 |
|---|---|
| 部署目標不同 | 混在一起就得在同一條 pipeline 裡判斷「這次改了誰」，很容易漏推或誤推 |
| 改動頻率不同 | dbt 模型幾乎天天改；VM1 腳本改一次穩很久。綁在一起會讓 VM1 每天被無謂重推 |
| 權限範圍不同 | VM1 腳本碰得到明碼資料與解密金鑰，review 的人不該完全是同一批 |
| 爆炸半徑 | VM1 推壞 = 資料進不來；dbt 推壞 = 名單算錯。要能各自 rollback |

**代價**：像「新增一張資料表」這種橫跨兩邊的事，要開**兩個 MR**。
這是刻意的取捨——寧可多開一個 MR，也不要讓兩台機器的部署互相綁死。

> ⚠️ 兩個 MR 要**一起**合併。只合併其中一個會出現
> 「Dagster 已經在叫一支 VM1 上還不存在的腳本」這種狀態。
> 做法見 [01_開發人員_日常開發流程 · 跨 repo 的改動](./日常維運/01_開發人員_日常開發流程.md#7-跨-repo-的改動要一起上)。

## 2. 誰在哪台機器上

| 機器 | 角色 | 這套流程裡負責什麼 |
|---|---|---|
| **VM3** | GitLab + Registry + Dependency-Track | 存 repo、跑 CI、跑 CD（rsync 的**發送端**）、伺服器端 pre-receive hook |
| **VM4** | Dagster | rsync 的**接收端**；`gitlab_runner` 收檔案，收完 chown 給 UID 10001 |
| **VM1** | BCP Pipeline | rsync 的**接收端**；`gitlab_runner` 收檔案，收完 chown 給 `bcp_runner` |
| **VM5** | Keycloak + Superset | 提供 GitLab 的 SSO 登入（不參與同步） |

**三台機器都要有 `gitlab_runner` 這個 OS 帳號**，但角色不同：

```
VM3 的 gitlab_runner  ← CD runner 的執行身分，持有兩把私鑰
        │
        ├─ ~/.ssh/gitlab_to_vm4  ──rsync──▶  VM4 的 gitlab_runner（只收）
        └─ ~/.ssh/gitlab_to_vm1  ──rsync──▶  VM1 的 gitlab_runner（只收）
```

VM1 / VM4 上的 `gitlab_runner` **不需要**私鑰，也**不需要**能登入其他機器——
它只是一個「收件人」。建立方式見
[附錄 A](./附錄/A_gitlab_runner帳號與SSH金鑰.md)。

> 📌 這跟原本 Dagster 用的 `dagster_user → bcp_runner` 是**兩條獨立的 SSH 通道**，
> 不要共用金鑰。Dagster 那條是「執行期指揮」，這條是「部署」，
> 用途、時機、風險都不同，出事時也要能分別停掉。

## 3. 四道資安關卡，順序很重要

使用者的核心要求是：**「不要等推上去了才掃，那時候錯的東西已經在 commit 裡了。」**

所以關卡是這樣排的：

| # | 在哪 | 什麼時候 | 擋得住什麼 | 能被繞過嗎 |
|---|---|---|---|---|
| 1 | 開發者本機 `pre-commit` | `git commit` 當下 | 金鑰進 commit 之前 | 能（`--no-verify`） |
| 2 | 開發者本機 `pre-push` | `git push` 當下 | 整批要推出去的 commit | 能（`--no-verify`） |
| 3 | **VM3 `pre-receive`** | **push 到達伺服器、但還沒寫進 repo** | **同上，但擋不掉** | **不能** |
| 4 | CI pipeline | push 成功之後 | 最後防線 + 稽核紀錄 | 不能，但**已經太晚** |

### 為什麼第 3 關才是真正的答案

git 收 push 的時候，物件會先落在**隔離區（quarantine）**：

```
開發者 push
     ↓
物件寫進 quarantine 暫存區（還不算數）
     ↓
執行 pre-receive hook
     ↓
   ┌─────────────┬──────────────┐
   ↓ 回傳 0      ↓ 回傳非 0
物件併入 repo    quarantine 整批丟棄
ref 前進         ref 不動
                 ★金鑰從頭到尾沒進過遠端 repo★
```

所以第 3 關被擋下來時：
- **不需要** `git filter-repo` 清歷史
- **不需要** 強制推送、通知全員重新 clone
- 開發者只要 `git rebase -i` 改掉自己本地的 commit 就好

而 CI 的 `secret-scanning` job（第 4 關）是 push **成功之後**才跑的，
那時候物件已經在 GitLab 的物件庫裡了。它的價值是稽核與最後防線，
**不是防護**。這也是為什麼不能只靠 CI。

> 三道 gitleaks 關卡跑的是**同一支 `ci/check_secrets.sh`、同一份 `.gitleaks.toml`**，
> 所以結果一定一致，不會出現「本地過了但被伺服器擋」這種令人抓狂的情況。
> pre-receive 甚至會優先讀「你這次推上來的那一份 `.gitleaks.toml`」，
> 所以修 allowlist 跟修程式碼可以放在同一個 commit 裡。

安裝方式見 [10_CI_Pipeline設定詳解](./進階調整/10_CI_Pipeline設定詳解.md)。

## 4. 測試與正式：同一個 GitLab，碰得到的東西不同

同一個 GitLab、同一個 repo，靠三件事把兩個環境隔開：

| 機制 | 做什麼 |
|---|---|
| **保護分支** | `main` 禁止直接 push，只能透過 MR 進來 |
| **Protected 變數** | 正式環境的連線資訊只有在**保護分支**上跑的 job 才拿得到 |
| **Environment scope** | 同一個變數名（如 `DEPLOY_HOST`）在 `production` / `staging` 有不同值 |

結果：

```
功能分支 / develop          main（保護分支）
     │                          │
     ▼                          ▼
 staging 變數                production 變數
     │                          │
     ▼                          ▼
  測試 DB                   正式 DB
  測試機                   VM1 / VM3 / VM4 / VM5
```

在功能分支上跑的 job **拿不到** production 的變數——不是「拿到但不該用」，
是 GitLab 根本不會注入。所以就算有人在測試分支寫了
`rsync 到正式機`，也會因為 `DEPLOY_HOST` 是空的而直接失敗。

> ⚠️ 這個保護的前提是 **變數有勾 Protected**。漏勾的話整套隔離就破功了。
> 檢查清單見 [13_Variables與環境隔離](./進階調整/13_Variables與環境隔離.md)。

## 5. 同步完整性：兩個時間點各對一次雜湊

| 時機 | 誰觸發 | 為什麼要有 |
|---|---|---|
| **部署完當下** | `ci/deploy_rsync.sh` 最後一步 | rsync 傳到一半斷線的話，當場就知道，不會讓 Dagster 拿半套程式碼跑一整晚 |
| **每天固定時間** | GitLab 排程 pipeline | 抓「部署完之後才發生」的漂移——最常見的是有人直接 ssh 上正式機改檔案 |

比對方式：兩端各跑同一支 `ci/sync_manifest.sh`，
對每個檔案算 sha256、排序、再對整份清單算一次 sha256。
排除規則用的是**跟 rsync 同一份 `deploy_exclude.txt`**，
所以 `.env`、`target/` 這些「本來就該不一樣」的東西不會誤報。

細節與排查步驟見 [12_同步完整性稽核](./進階調整/12_同步完整性稽核.md)。

## 6. 一次改動的完整路徑

```
1. 開發者本機
     git checkout -b feat/xxx
     改檔案
     git commit        ← [關卡1] pre-commit：gitleaks --staged
     git push          ← [關卡2] pre-push：掃整批 commit + 工作目錄
                          （flake8 / bandit / sqlfluff 只掃你動到的檔案）
2. VM3 GitLab
     收到 push         ← [關卡3] pre-receive：★繞不過★ 有金鑰就直接拒絕
     開 MR (→ main)
     CI pipeline       ← [關卡4] lint / test / gitleaks 全歷史 / bandit / D-Track SBOM
     Code Review       ← 正式環境必經，至少一位不是作者的人看過
     合併 main
3. VM3 CD runner（gitlab_runner）
     rsync --delete --checksum  →  VM4 或 VM1
     ssh 執行 post_deploy       →  chown + 重產 dbt manifest / 語法檢查
     驗雜湊                     →  不一致就讓 pipeline 紅燈
4. 開發者
     到 Dagster UI 做 Reload definitions（只有 dagster-workspace 需要）
5. 隔天
     排程 pipeline 再對一次雜湊
```

## 7. 這套機制守不住什麼（要知道邊界）

誠實列出來，免得誤以為裝了就萬無一失：

| 守不住 | 說明 | 補償措施 |
|---|---|---|
| main 分支本身被塞壞東西 | 如果 review 沒看出問題，CI 也沒抓到，它就會被部署 | 靠 code review 品質；正式環境要求 review 者不是作者 |
| 有人在正式機上改完又改回去 | 雜湊在下次對帳時已經一致 | 檔案系統稽核（auditd）、rsyslog 的 ssh 登入紀錄 |
| 被排除的檔案（`.env`）被竄改 | 排除清單裡的東西不比對 | 那些檔案要另外做權限控管（600 + 只有 root/服務帳號可讀） |
| 拿到 CD 私鑰的人 | 可以直接 rsync 上正式機 | 金鑰只放在 VM3 的 `gitlab_runner` home、600 權限、`from=` 限制來源 IP、定期輪替 |
| GitLab 本身被入侵 | 整條信任鏈的根 | 不在本手冊範圍，屬主機安全 |
