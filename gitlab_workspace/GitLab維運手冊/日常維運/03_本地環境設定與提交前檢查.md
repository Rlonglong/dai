# 03 · 本地環境設定與提交前檢查

新機器、新同事，clone 完之後照這篇做一次就好。

---

## 1. 為什麼要在本地裝檢查

因為**東西一旦推上 GitLab，就算刪掉也還在歷史裡**。

金鑰進了 remote repo，處理成本是：

1. 把金鑰作廢、換一把新的（無論你有沒有刪掉檔案，它都已經外洩了）
2. 用 `git filter-repo` 重寫整條歷史
3. 強制推送
4. 通知**所有人**刪掉本地 clone、重新 clone
5. 資安通報

如果在本地就擋下來，成本是：`git reset` 或 `git rebase -i`，三十秒。

> 順帶一提：就算你不裝，VM3 的伺服器端 hook 還是會擋（那個繞不過）。
> 裝本地 hook 純粹是為了讓你**早一點**知道，不用等到 push 被拒。

## 2. 安裝

### 2-1. Python 虛擬環境

```bash
python3.11 -m venv ~/.venv
source ~/.venv/bin/activate

# 離線環境：先把 wheel 帶進來
pip install --no-index --find-links=<wheel目錄> \
    black flake8 bandit sqlfluff pip-audit cyclonedx-bom
```

`~/.venv` 這個路徑是 hook 預設會找的位置。放別的地方的話：

```bash
echo 'export DAI_VENV=/your/path/to/venv' >> ~/.bashrc
```

### 2-2. gitleaks

**這是唯一不可缺的工具**——沒有它 hook 會直接擋下所有 commit 和 push
（而不是「跳過檢查放行」，那樣太危險）。

```bash
# 離線環境：從內部檔案伺服器取得 binary
install -m 755 gitleaks ~/.local/bin/gitleaks

# 確認
gitleaks version
```

放在別的路徑：

```bash
echo 'export GITLEAKS_BIN=/opt/tools/gitleaks' >> ~/.bashrc
```

### 2-3. 裝 hook

```bash
cd <repo>
ci/install_hooks.sh
```

輸出會列出每個工具的狀態：

```
  工具         狀態
  ----         ----
  gitleaks     ✅ /home/rlong/.local/bin/gitleaks
  flake8       ✅ /home/rlong/.venv/bin/flake8
  bandit       ✅ /home/rlong/.venv/bin/bandit
  sqlfluff     ✅ /home/rlong/.venv/bin/sqlfluff
  black        ✅ /home/rlong/.venv/bin/black
  pip-audit    ❌ 未安裝
```

`❌` 的工具，hook 會印警告然後**跳過那一項**（gitleaks 除外）。
所以看到 `❌` 不代表壞掉，但代表那一項檢查要等到 CI 才會跑。

### 2-4. 確認裝好了

```bash
ci/install_hooks.sh --check
```

> 💡 `install_hooks.sh` 是設 `core.hooksPath` 指向 `ci/hooks/`，
> **不是**複製檔案到 `.git/hooks/`。
> 好處是 hook 內容跟著 repo 版控，改了大家 `git pull` 就同步生效，
> 不會出現「有人的機器上還是三個月前的舊 hook」。

## 3. 每一關在檢查什麼

| 時機 | 誰跑 | 掃描範圍 | 可以跳過嗎 |
|---|---|---|---|
| `git commit` | pre-commit | staged 的內容 | 品質可以，gitleaks 不行 |
| `git push` | pre-push | **整批要推出去的 commit** + 工作目錄 | 品質可以，gitleaks 不行 |
| push 到達 VM3 | pre-receive | 同上 | **完全不行** |
| push 成功後 | CI pipeline | 全樹 + 全歷史 | 不行 |

### 跳過品質檢查

```bash
DAI_SKIP_QUALITY=1 git commit -m "..."
DAI_SKIP_QUALITY=1 git push
```

只跳過 flake8 / bandit / sqlfluff / black。**gitleaks 永遠會跑**。

### `--no-verify` 為什麼沒用

```bash
git push --no-verify        # 跳過本地 hook
                            # ↓
                            # VM3 的 pre-receive 還是會掃
                            # ↓
                            # ! [remote rejected] ... (pre-receive hook declined)
```

伺服器端跑的是**同一支 `ci/check_secrets.sh`、同一份 `.gitleaks.toml`**，
所以結果一定一致。與其被伺服器拒絕，不如在本地就修掉。

## 4. 被擋住的時候怎麼修

### 4-1. gitleaks 說有金鑰

```
[FAIL]  Gitleaks 掃描失敗！在「尚未推送的 commit」發現 1 個疑似金鑰。

  [1] dai-db-connection-password
      檔案  : dagster_workspace/dagster_code/db_test.py:12
      commit: a3f2b91c4e05  作者: rlong
      內容  : DB_PASS=****
```

**真的是金鑰：**

```bash
# 1. 先去把那把金鑰作廢、換一把（這一步不能省）

# 2. 從程式碼移除，改讀環境變數
#    VM4 → dagster_workspace/dagster_code/.env
#    VM1 → /home/bcp_runner/.env
#    這兩個檔案都在 .gitignore 和 rsync 排除清單裡

# 3. 如果還沒 push（大部分情況）
git rebase -i a3f2b91c4e05^      # 改掉那個 commit
# 或者整批重做
git reset --soft HEAD~3 && git commit -m "..."

# 4. 已經 push 上去了（表示 hook 沒裝，或有人 --no-verify）
#    這時候要重寫歷史，先跟系統負責人聯絡，不要自己動
```

**確定是誤判**（例如範本檔裡的假值）：

改 repo 根目錄的 `.gitleaks.toml`，在 `[allowlist]` 加一條**最小範圍**的 regex：

```toml
[allowlist]
regexes = [
    # ... 既有的 ...
    # 說明為什麼這是安全的：這是 XXX 文件裡的示範用假值
    '''DEMO_KEY_FOR_DOCS_ONLY''',
]
```

然後**跟你的程式碼改動放在同一個 commit 裡**——
伺服器端的 hook 會優先讀「你這次推上來的那一份設定」，所以會一起生效。

> ❌ 不要用 `paths` 把整個檔案或整個目錄放行。
> 那等於以後那個路徑底下永遠不掃了，真的漏金鑰也不會知道。

### 4-2. flake8

```
| dagster_workspace/dagster_code/assets.py:8:1: F401 'pandas as pd' imported but unused
```

照著改就好。設定在 `.flake8`（`max-line-length = 120`）。

### 4-3. black

```
| would reformat dagster_workspace/dagster_code/table_mapping.py
```

```bash
black dagster_workspace/dagster_code/table_mapping.py
```

> ⚠️ **第一次導入時的已知狀況**：既有程式碼是在導入 black 之前寫的，
> 所以你只要動到某個舊檔案，black 就會要求整檔重新格式化，
> diff 會突然變得很大。
>
> 解法是先做一次**全庫格式化**，單獨開一個 MR：
> ```bash
> ci/format_all.sh
> git checkout -b chore/format-all
> git commit -am "chore: 全庫套用 black / sqlfluff 格式（無邏輯改動）"
> ```
> 這件事做過一次之後就不會再遇到了。

### 4-4. sqlfluff

```
| L:  12 | P:   5 | CP01 | Keywords must be upper case.
```

大部分可以自動修：

```bash
sqlfluff fix --processes 1 <檔案>
```

**修完一定要看 diff**——`fix` 會動到 SQL 語意上無關但視覺上很大的地方。
改完建議 `dbt compile` 一次，確認編譯結果跟修之前一樣。

### 4-5. bandit

```
| >> Issue: [B608:hardcoded_sql_expressions] Possible SQL injection vector
```

這類通常是真的要處理，不是誤判。用參數化查詢取代字串拼接。

真的必須這樣寫（例如表名不能參數化），加 `# nosec` 並**寫清楚理由**：

```python
# nosec B608 - 表名來自 TABLE_CSV_MAPPING 的白名單，不接受外部輸入
cursor.execute(f"SELECT COUNT(*) FROM [{table_name}]")
```

`# nosec` 會在 review 時被特別注意，理由寫不清楚 reviewer 會退回。

## 5. 常見問題

| 症狀 | 原因 | 解法 |
|---|---|---|
| `commit` 沒有跑任何檢查 | hook 沒裝 | `ci/install_hooks.sh` |
| `找不到 gitleaks 執行檔` | 不在 PATH | `export GITLEAKS_BIN=/path/to/gitleaks` |
| hook 跑但工具全部 `⚠️ 找不到` | venv 沒啟動 | `source ~/.venv/bin/activate`，或設 `DAI_VENV` |
| push 很慢 | 第一次 push 新分支會掃整批 commit | 正常，之後只掃增量 |
| `[remote rejected] (pre-receive hook declined)` | 伺服器端擋下 | 看錯誤訊息裡列的檔案，照 4-1 處理 |
| Windows 上 hook 沒作用 | 換行符 / 執行權限 | 用 Git Bash 或 WSL；`chmod +x ci/hooks/*` |
| `._foo.py` 被掃出一堆錯 | macOS AppleDouble 檔 | hook 已自動過濾；`.gitignore` 也擋了。已經 add 進去的話 `git rm --cached` |
